# 开发难点档案（小标题 & 美术资产维度）

> 定位：记录 wechat-mp 在**小标题情景细化 → 美术资产体系**这个维度开发中遇到的全部难点（现象 → 根因 → 解法 → 教训）。
> 用途：①转正/扩展时避免重蹈覆辙；②复盘"为什么踩坑"；③沉淀成可复用的开发经验。
> 时间范围：2026-08-29，覆盖 v1 → v5（第 0-5 轮）全部开发活动。
> 依据：test/ 各轮记录 + PROGRESS.md 详细条目 + 实际排障过程。

## 一、需求理解类难点（用户反馈驱动的方向纠偏）

| # | 难点 | 根因 | 解法与教训 |
|---|---|---|---|
| D1 | 调研把小标题写法做成了**主标题写法**（悬念/煽情/爆款数字） | 未区分"主标题=点开、文内小标题=读下去"两套体系，把标题党公式套到文内 | 专项重调研（20 来源），确立两套体系分界；**教训：同类概念先分清"场景/职责"再调研，避免概念混淆污染结果** |
| D2 | 装饰密度上限过于保守（"每屏 ≤1 处"） | 凭直觉定上限，没有真实数据支撑 | 18 来源 + 1 篇真实推文 HTML 实测（58 图/25 背景/530 区块 ≈ 每屏 4-6 视觉元素）；**教训：设计约束必须有实测依据，不能拍脑袋** |
| D3 | 素材"太过简单"（用户第 2 次反馈） | 把"平面化铁律"误读为"简单线条即可"，忽略了精致度 | 引入渐变+明暗分层（SVG 内合法，正文 CSS 平面化不受影响）；**教训：v10 铁律限制的是正文 CSS，资产是 PNG 图片，两者边界要分清** |
| D4 | 素材"依旧不好看"（用户第 3 次反馈） | 复杂度达标 ≠ 视觉美观；装饰尺寸小到看不见 | 显示尺寸铁律 + 精细度 ×4 铁律；**教训：美=尺寸+精细度+层次，缺一不可；先保"看得见"再谈"好看"** |
| D5 | "花纹小到根本看不见"（用户第 4 次反馈） | **设计像素未按显示缩放比反推**——画布 600-750px，375px 壳显示仅 179-343px（缩放 0.4-0.6），设计 5px 的装饰缩放后仅 2-3px | 建立"设计像素 = 目标显示像素 ÷ 缩放比"公式；**教训：设计 SVG 时必须先算目标显示尺寸，不能只对着画布看比例** |
| D6 | "画面太丑，精细度 ×4"（用户第 5 次反馈） | 装饰元素只有 1-2 个部件、渐变 2-3 stop、无高光/纹理 | 建立精细度标准（4 层花瓣+花蕊丝/4-6 stop 渐变/叶侧脉/珍珠双高光/S 形卷曲）+ 渲染 4x；**教训：精致度是可量化的（层数/stop 数/部件数），定义标准后批量执行** |

## 二、SVG 渲染与设计类难点

| # | 难点 | 现象 | 根因 | 解法 |
|---|---|---|---|---|
| S1 | probe 落在**曲线间隙/装饰虚线**上 | 初选检查点 9/38 失败 | probe 点恰好在贝塞尔曲线空隙、波浪低谷、dasharray 虚线间隔 | probe 必须选**确定着色**的位置（花瓣主体/线实段/实心圆点），避开曲线端点、虚线、间隙 |
| S2 | probe 落在**花心白色高光**上 | 花瓣中心采样到 (241,229,224) 而非深色 | flower5X 中心有 r×0.15 白色高光圆（opacity 0.85），叠加在花心上 | probe 移到花心深色环（距中心 r×0.3 处，白点外/花心内）；**教训：带高光/白点的装饰，probe 必须避开高光半径** |
| S3 | probe 落在**渐变中段色**上 | 期望纯色但采到混合色 | 渐变（linear/radial）中段的 RGB 是插值，不可预测 | probe 只选**纯色部件**（花心/线实段/端点圆/框线），或把期望色校准为实测渐变值（容差 ±12） |
| S4 | 夹线中心花被**嵌字文字遮断** | combo-clamp-flower 中心花饰在嵌字区 | 嵌字时文字用 background:#fff 遮断线，中心花恰在文字下方 | **装饰必须避开文字区**（中央留空 ≥260px，装饰放线端/角部）——铁律 |
| S5 | `<line>` 元素 + objectBoundingBox 渐变**渲染退化** | 升级后线条资产不透明率骤降到 0.2%，probe 全透明 | `<line>` 的 bbox 高度为 0，objectBoundingBox 渐变在 y 方向退化 | 线渐变必须 `gradientUnits="userSpaceOnUse"` + 绝对坐标（x2=画布宽）；**教训：细线元素配渐变必须用 userSpaceOnUse** |
| S6 | 渐变 stop-color **丢失 # 前缀** | 升级脚本生成的 stop 无效，SVG 渲染异常 | 正则捕获组不含 `#`，替换时未补回 | 写转换脚本时先验证"输出能否被原始正则再次匹配"（幂等性检查） |
| S7 | 升级脚本**误删 `</svg>\`` 结尾** | 整文件语法错误（Unexpected identifier 'xmlns'） | 正则捕获组把 `</svg>\`` 吞掉，替换时未保留 | 脚本替换大段文本后必须立即 `import` 验证语法；**教训：批量文本替换要带语法自检** |
| S8 | 升级脚本**重复执行破坏渐变** | 同一资产跑了两次脚本，渐变只剩 1 个 stop | 脚本不幂等：第二次执行时正则匹配了已生成的内容并二次插值 | 升级脚本必须幂等（已升级的串不再匹配）；用"完成 N 处"输出核对 |
| S9 | 花被放大后的**叶子覆盖** | combo-accent-branch 花心采到叶子渐变 | SVG 绘制顺序：叶子在花之后绘制，放大后叶覆盖花心 | 花要画在装饰最上层（flower5X 放 leafX 之后）；**教训：放大装饰时要复查元素 z 顺序** |
| S10 | **贝塞尔曲线位置**与预期不符 | probe (300,44) 透明，线实际在 y=46 | `C 160 44 360 44 490 52` 曲线在 x=300 处 y≈46，stroke 半宽不够覆盖 y=44 | probe 前先渲染扫描线实际位置（行扫描找非透明 y 范围）；**教训：曲线/弧线 probe 要实测，不能按端点猜** |
| S11 | 徽章数字/字符间隙**误报透明** | verify 检查点落在 "01" 两数字间空隙 | text 渲染有字符间隙 | 用诊断脚本先确认文字笔画实际位置（x=40 '0' 笔画纯白），再定检查点 |
| S12 | 徽章虚线环 probe 不稳定 | dasharray 环上采样点可能落在间隙 | 虚线环 4 5 周期，角度不同落点不同 | 虚线环改实线环（laurel），或 probe 用花心/主体纯色 |
| S13 | flower5X 白点偏移使旧 probe 失效 | 升级后 probe 采到浅色（花瓣渐变） | 白点位置改为 (cx-r×0.1, cy-r×0.1)，旧 probe 距中心 4-6px 落在花瓣上 | 重校准：花心深色环位置（距中心 1.4-2.2px 避开白点） |
| S14 | 徽章主体出现**大白色圆圈**（用户报"为什么徽章上有白色圆圈"） | 徽章中心偏上出现 r≈11.5-12.2 的白色半透明圆 | **批量升级脚本把"圆点加高光"的正则作用于所有 circle（r≥5），徽章主体大圆（r=36-38）被误当成装饰圆点，加了白色高光**；且脚本重复执行时高光叠加成 2 个 | 高光正则必须限定 r 上限（仅装饰小圆 r≤10 加高光）；修复：删除徽章主体圆上的误加白圈（3 个徽章 × 重复 2 次 = 6 处）；**教训：批量正则升级必须限定匹配范围（尺寸/语义），大形状不能套用小装饰规则** |

## 三、自动化验证脚本类难点（Playwright / 像素验证）

| # | 难点 | 现象 | 根因 | 解法 |
|---|---|---|---|---|
| V1 | 找不到 playwright / chromium | `browserType.launch` 报默认 headless shell 不存在 | `existsSync` 只在 loadPlaywright 内导入，findChromium 里未定义被 catch 吞掉返回 undefined | 顶层导入 existsSync；**教训：工具函数引用的依赖必须在同一作用域导入** |
| V2 | page.evaluate 里用 Node API | `readFileSync is not defined` | 浏览器上下文没有 Node 模块 | Node 侧读文件 → base64 传入 evaluate；**教训：evaluate 内只能用浏览器 API** |
| V3 | 截图尺寸与预期不符 | 截图 375×2091 而非 2x | deviceScaleFactor 与 fullPage 截图组合的像素比不确定 | 用 DOM bbox + 截图自然尺寸动态映射（sx = imgW/375） |
| V4 | 中心点采样落在**透明/空白区** | 资产中心是镂空（框内透明） | 装饰分布不居中（如夹线两端、框四角） | 改**包围盒扫描**（对 img bbox 区域统计非白像素占比），不采单点 |
| V5 | 细线资产不透明率 <1% 被误判失败 | frame-lines 0.91% 判 FAIL | 细线框类资产天然低占比 | 阈值分级：细线类 0.5%，插画类 1% |
| V6 | 诊断脚本统计**全局最小元素**误导 | "最小装饰 0.6px" 判定全部 SMALL | 统计了花心白色高光（r×0.15）等本就细微的元素 | 诊断要看主装饰（花/叶/珍珠）的实际显示尺寸，排除高光/叶脉等纹理细节 |
| V7 | PowerShell 内联 node -e 转义地狱 | 正则/引号被 PS 吃掉（`\"` 变 `"`） | PS 与 JS 引号规则冲突 | 复杂脚本一律写 .mjs 文件运行，不用 -e 内联 |
| V8 | 校准脚本**回写失败** | 校准输出"回写 N 处"但文件 probe 未变 | 正则匹配 `[x,y,COLOR]` 常量格式，而文件已是 `[x,y,[r,g,b]]` 数组格式 | 回写用"按资产名定位 probe 行 → 截断到行尾替换"的稳健方式 |
| V9 | 校准脚本 **ReferenceError: pos is not defined** | evaluate 内局部变量在外部访问 | 变量作用域误用 | evaluate 返回值必须在内部构造并 return |
| V10 | probe 校准后渲染仍失败 | 校准色与渲染色不一致 | 校准读的是修改前文件（渲染脚本重写文件），或校准值本身是透明查找的伪值 | 校准-渲染-再校准闭环，直到 0 校准输出 |

## 四、文件编辑与文档同步类难点

| # | 难点 | 现象 | 根因 | 解法 |
|---|---|---|---|---|
| E1 | 编辑顺序 bug（banner-flag vs banner-scroll） | 假设文件里 scroll 在前，实际 flag 在前 | 未核对实际行序 | 批量编辑前先 grep 确认目标行实际位置；**教训：文件内容顺序 ≠ 记忆中的顺序** |
| E2 | README 结构被破坏 | 替换后 `## 一、` 标题消失 | replace 的 old_string 把标题行吞掉 | 替换后重读文件确认结构完整 |
| E3 | 相同 probe 字符串误改**第一个匹配** | A1 被误改而非 A4（两者 probe 相同） | `String.replace` 默认只替换第一个匹配 | 修复脚本用**唯一上下文**（name 行 + probe 行一起匹配），或逐资产定位 |
| E4 | 文件被脚本修改后 edit 工具拒绝 | "file changed since it was read" | 脚本改文件后工具缓存过期 | 脚本操作后先 read 再 edit |
| E5 | STRUCTURE.md / CLAUDE.md 编辑前必须 read | 直接 edit 报错 | 工具要求先读 | 遵守工具契约：先 read 再 edit |
| E6 | 文档数字多处不同步（12→38、39→77→85→106） | README 里旧数字残留 | 多轮迭代未全量更新 | 每轮结束用 grep 搜旧数字确认清零 |
| E7 | **主智能体与子智能体并发写同一文件**（divider 第 10 轮） | 主智能体为通过验证临时放宽扫描器校验（严格相等→上限），子智能体运行中发现声明值被改写 | 后台子智能体仍在 running 时主智能体介入修改其产出文件 | 子智能体用**独立扫描器 + EXPECT 声明值守卫**（声明被篡改即中止）对抗；主智能体介入前先确认子智能体已停止，或只做只读检查 |

## 五、设计体系类难点（概念层面）

| # | 难点 | 现象 | 根因 | 解法 |
|---|---|---|---|---|
| C1 | 装饰方向（上划线 vs 下划线） | 用户指出"上划线式少见，夹线必须嵌字" | 把分隔线/夹线放在标题上方（overline），真实推文主流是下置（下划线式）或夹线嵌字 | 线条方向铁律：下置为常态、夹线嵌字（线断于文字两侧）、禁上划线式 |
| C2 | 组件行距双重留白 | "小标题上下有线条分割，又多了宽空行" | 组件自带线条分隔时仍按普通段落加宽 margin | 组件行距铁律：自带线条时四周空行收紧（组件与正文 12-20px、标题与装饰线 6-8px） |
| C3 | 组件化思维缺失 | 素材与文字割裂，"贴上去"感 | 未按"组件=美术素材+文字"设计 | design-logic-components 顶层方法论 + 组合模板体系（combo-* 完整组件底图） |
| C4 | 数字徽章编号不可复用 | 数字是 SVG `<text>` 占位"01"，改号要重渲染 | 资产是 PNG，文字已固化 | 文档说明：改编号需改 SVG 源后重渲染上传（微信 URL 永久有效） |
| C5 | 可换色 vs 精细度冲突 | 单色纯平面资产可程序化换色，但太简单 | 换色逻辑假设纯色填充 | 渐变用**同色相明暗**（浅→主→深），换色时整体替换色板仍成立 |
| C6 | 子智能体"验证通过"≠"用户满意" | 子智能体报告 10/10 全绿，但 375px 壳叠字全越界 | 子智能体只验"zone 内无装饰侵入"，没把真实文字叠进去验"zone 装得下文字" | **三层验证闭环**：资产级 probe + zone 洁净扫描 + 375px 壳叠字 DOM 实测（文字边界在 zone 内） |
| C7 | 子智能体缺"整图资产"尺寸常识 | 画布 750×150、嵌字区 27px 显示高，装不下两行文字 | 知识文件只有 CSS 骨架参数（padding/字号），没给整图资产画布/zone 规范 | **§五 5.0 整图资产构建规范**：画布 750×215、zone 设计高 ≥120px（y50..170）、设计宽 ≥620px；双泡每泡 ≥72px 一行字 |
| C8 | 大面积渐变方向导致 PNG 超限 | 水平背景渐变 4x 渲染 1309KB >1MB | 水平渐变每行像素全不同，PNG 熵爆炸 | 大面积背景渐变用**垂直方向**（实测 ≤348KB）；仍 userSpaceOnUse + 绝对坐标 |
| C9 | 子智能体任务应"一次做对" | 需要主智能体两轮返工修正 | 任务 prompt 未把历史失败教训显式化 | 任务注入改进后知识文件（含失败反例），要求三层验证 10/10 才交付；主智能体独立验收兜底 |
| C10 | **行内 art:// 小图与文字基线脱离**（第 12 轮，用户反馈"行首小花飘到第一行上面"） | `inline()` 对 art:// 统一输出整幅装饰样式（max-width:56% + vertical-align:middle + margin:12px）→ 行首小花放大成 192×105px 巨盒；旧资产图案在画布内位置无契约 | 渲染器未区分"独立成行整幅装饰"与"随文字排布的行内点缀"；资产只按整幅场景设计，无底部锚点概念 | **行内装饰三板斧**：①语法 `art://名称:px` 给显示高（缺省 16px）②资产紧裁 ≥70% + 图案底贴画布底（≤5px 设计）③渲染 CSS `vertical-align:baseline;margin:0 3px 0 0`；独立成行 art:// 保持居中 56% 不变；像素带验证（图底 vs 同行文字底差 ≤4px） |

## 六、经验沉淀（可复用规则清单）

1. **设计尺寸公式**：设计像素 = 目标显示像素 ÷ 缩放比；先定显示尺寸再画 SVG。
2. **probe 选址铁律**：只选纯色部件；避开白点/渐变中段/虚线/曲线端点/间隙；花心类选深色环（距中心 r×0.3）。
3. **细线渐变**：`<line>` 配渐变必须 `gradientUnits="userSpaceOnUse"`。
4. **嵌字避让**：装饰放文字区外（中央留空 ≥260px）。
5. **z 顺序**：花/主体装饰画在叶子等覆盖物之上。
6. **批量脚本三检查**：幂等性、输出完整性（`</svg>` 不丢）、改后立即 import 验语法。
7. **校准闭环**：校准 → 渲染 → 再校准，直到 0 输出。
8. **evaluate 边界**：Node API 不出 evaluate；返回值在内部构造。
9. **文档同步**：每轮结束 grep 旧数字/旧名称确认清零。
10. **铁律分级**：正文 CSS 平面化（渐变/阴影/emoji 禁）≠ 资产 PNG 内渐变/高光（合法），两者边界勿混。
11. **子智能体交付标准**：验证维度 = 用户验收维度。子智能体自报"全绿"前，先问"用户会怎么检查"——375px 壳截图、真实文案叠入、体积、颜色对比度，逐项对齐。
12. **知识文件=子智能体的唯一规范**：子智能体无会话记忆，任务 prompt 必须注入完整知识文件（含历史失败反例），不能假设它"知道常识"。
13. **主智能体独立验收兜底**：子智能体产出后，主智能体用独立脚本（非子智能体自报）核验关键指标，避免"自证清白"。
14. **行内小图 vs 整幅大图两条管线**：行内点缀必须给显示高（px）+ 基线对齐 + 底部锚点资产；独立成行装饰走整幅居中。渲染器一条样式通吃两类场景必然出问题——渲染分支先分场景再定样式。
