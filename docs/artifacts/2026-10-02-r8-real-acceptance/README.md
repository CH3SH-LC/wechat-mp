## 二、过程中两次真实失败与修复（都经"停止归档 → 定位 → 修 → 复验"）

### 失败 1：模型把 3 次 prep 预算全花在知识工具上（exe `64ab2946…`）

- 现象：L1 三次派发全为 `load_knowledge`/`search_knowledge`/`search_assets`，**一次 `finish_preparation` 都没有**；
  应用按设计报「准备阶段 3 次请求内没有得到合法的结果声明」，**未写稿、旧成品不变**（如实失败，没有假成功）。
  证据：`%TEMP%/wxmp-live-r6-1790949043/evidence/L1-2026-10-02T13-50-43-a1086c95/`。
- 对照：同题面在上午的验收版上跑过 3 个会话，termination **恰好都落在第 3 次**——预算是零余量的。
- 根因：`src/lib/prep.ts` 的 `PREP_INSTRUCTION` 里写着「取完后若仍有影响成稿的关键点没弄清楚，就用自然对话问清楚
  （**可以继续问，不必一次问完**）」，没有说明"每轮必须以 `finish_preparation` 收尾"，模型照字面执行即超预算。
- 修：收紧指令（写明请求次数有限、必须尽快声明、不要用"再取一轮"代替提问），并新增
  `PREP_LAST_ROUND_REMINDER`——**只在最后一次准备请求**追加"不要再取资料，现在就声明"。
  总额仍是 3 次、没有第 4 次（不放宽契约）；触发条件是"这是第几次请求"这个执行计数，不读对话意图、不做路由。

### 失败 2：模型在同一条回复里混用知识工具与终结工具（exe `a33a0179…`）

- 现象：L4 的唯一一次 prep 响应是 `load_knowledge + load_knowledge + finish_preparation`；
  契约规定"一份响应只接受知识工具集合或一次终结"，混用判协议错误 → **没有换图、没有新 revision**。
  证据：`%TEMP%/wxmp-live-r7-1790950084/evidence/L4-*`。同批 L1/L2/L3 均未混用（4 次会话里 1 次）。
- 根因：**上一处修改的措辞引入了歧义**——「这些点尽量在同一次回复里并列取全」＋「每一次回复都必须以
  `finish_preparation` 收尾」合起来可以读成"在同一条回复里既取资料又声明"，而当时指令里**没有**禁止混用。
- 修：指令改为「**知识工具与 `finish_preparation` 不能出现在同一条回复里**：先把资料取完，**取完之后的下一条回复**
  再声明」，并保留了顺序语义。

### 回归（先证红）

`scripts/prep-contract-check.mjs`（真实 `runPrep` + stub `prep_turn`）：

- 新增用例 `exhausted-knowledge-only`：三轮全知识工具 → 必须 `failed/exhausted` 且**无第 4 次请求**
  （第 4 条返回是哨兵）。这也是"预算提醒真的发出去"的唯一非空样本。
- 新增断言：**最后一次准备请求真的带上预算提醒、且只出现在最后一次**（按每次实际发出的消息计数）。
  变异（把提醒条件改成恒假）→ 该断言红：`各次提醒条数=[0,0,0]，期望=[0,0,1]`。
- 新增断言：**首次请求就声明了"知识工具与终结工具不能同一条回复"**（按实际发出的消息断言，不是查源码文本）。
  变异（把该句改掉）→ 全部用例红。两次变异均已还原。
- `prep-contract-check` PASS、`repair-flow-check` PASS、`verify-ui` **134/134**、`tsc` 干净。

## 三、如实记录的两处不完美

   也不撤销后来的通过；后续出现即按"关停偶发"单独排查（真实工作区与成品未受影响）。
2. **模型仍然正好用满第 3 轮才声明**（L1 与历史一致）。预算提醒已确认实际发出，但**本次无法证明它就是
   通过的决定因素**——只能证明"提醒确实在最后一次请求里发出去了"，以及收紧后的指令没有再诱发混用。
