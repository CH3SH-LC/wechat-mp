## 1. 任务目标与当前结论

修复本轮实测中“模型输出、界面成功提示、实际成品不是同一回事”的两条主链路，并补齐能发现它们的验收。最终应满足：

1. 模型决定开始创作或已经提供完整稿件后，该稿必须进入统一的素材解析、质量检查、版本提交流程；不能只存聊天消息。
2. 自动修复不能删改关键事实后仍提交成品；合法的去 emoji、时间格式统一、句式调整又不能被误杀。
3. 用户只改文字时，真正提交一份新版本，并保持现有素材身份和快照，新增绘图为 0。
4. “已保存”“已更新”来自本轮提交回执；当前显示旧成品不能被当作本轮操作成功。
5. 流式候选进入预览时，不发起当前产品规则禁止的外链资源请求；原始违规证据仍进入质检。
6. 验收脚本根据新版本、源文、HTML、绑定、快照与本轮请求记录判定，不以退出码、绿色条或助手话术代替业务结果。

本轮已确认首篇图文创作、单图生成入库、HTML/750px PNG 导出、正常关闭重开可以成功。这些结果保留。后端 131 项、九项离线 473 条、浏览器 107 条业务断言通过，**并不能覆盖下述真实失败**；浏览器总检查另有 1 项网络错误，原始结果为失败。

## 3. 包 A：先把失败变成真正的回归

### 3.1 保存原证据，另建本次输出

`EVIDENCE/offline/repair-fact-loss-probe.mjs` 是**确认缺陷的调查探针**：其 exit 0 可能表示成功观察到了错误，并不表示产品通过。它还硬编码 `repair-fact-loss-v2` 输出目录。`prep-ready-probe` 同样记录的是旧行为。

实施时将必要输入迁入仓库测试夹具，测试断言改为**期望的正确行为**，用新目录写结果；不得直接重跑旧脚本覆盖原证据。原始输入保持不变，记录适配差异。生产模块变化时更新导入或观察接口，不把实现复制进测试。

建议新增以下入口，名称可调整但文档和命令须同步；这些是待实现项，不是当前已存在的命令：

- `scripts/repair-integrity-check.mjs`：事实规范化、严重度与候选决策纯函数。
- `scripts/repair-flow-check.mjs`：当前 App 受控输出，验证事实丢失不提交、保留事实能提交。
- `scripts/prep-contract-check.mjs`：真实 `runPrep`，注入 Rust invoke 的响应；不走浏览器 `mode:'skip'`。
- `scripts/preview-resource-check.mjs`：从生成开始观察未经许可的资源请求。
- 真实桌面 runner：统一业务断言及结构化结果，使用新的隔离启动器。

先在旧实现跑出预期的红，再改实现。至少对“去掉正文检查”“恢复 substring 匹配”“把候选提前纳入 best”“恢复非 READY 全部澄清”做有界变异确认；只在隔离副本进行，恢复后核对源码指纹。

### 3.2 唯一业务判定器

同一份检查结果同时决定进程退出码、JSON 结果和总结。汇总器不得另写更弱的 `passed` 条件；缺失字段为 UNKNOWN，不能自动通过。

每例至少记录：输入、预期、实际断言、失败原因、测试脚本哈希、被测源码指纹、sessionId、runId、基准/结果 revisionId、开始/结束时间、请求与绘图计数、原始 trace、源文/HTML/绑定/快照/manifest、截图及环境异常。

成功须证明**本轮行为**发生；已有 `accepted` 旧稿、没有新绘图、助手出现新消息都不是续改成功的充分条件。普通问答或取消的正确结果反而是文档没有新提交，须按用例分别断言。

## 4. 包 B：自动修复的事实保护

### 4.1 源码根因

`App.tsx` 第 969 行建立 `baselineHtml=null`；第 985 行仅在候选没有阻断时设置基准，而第 1006 行同条件立即退出。能进入自动修复的路径始终没有基准。`evaluate` 第 898 行传入空正文比较，第 1031 行的退化检查不可达。

此外，第 984 行在退化检查之前 `best=better(best,cand)`；成功退出和预算上限也位于退化检查之前。只改基准初始化不能修复候选选择次序。

`delivery-quality.ts` 还有两种独立问题：

- `bodyIntegrity.ok` 因任意片段丢失变为 false，但 `issuesFromBody` 将普通片段丢失列为 warning；最终 gate 仍使用 false，形成没有阻断项却不能通过的矛盾。
- 姓名抽取包含上下文虚词，事实是否存在则依赖 `afterAll.includes(f.text)`；既会把同义改写误判，也会漏掉时间/电话边界变化。

### 4.2 分开三份对象

| 对象 | 来源与生命周期 | 用途 |
| --- | --- | --- |
| `priorAccepted` | 回合开始前读取的上一份完整已验收版本 | 失败后恢复 source/HTML/绑定/快照，不能只留旧 HTML |
| `repairBaseline` | 当前用户回合首个候选的可信正文事实；建立后冻结 | 后续自动修复必须保留的事实，不要求首稿零视觉/排版阻断 |
| `previousAdmissibleCandidate` | 本修复链最近一个未被退化判断否决的候选 | 比较新问题与进展，不得拿已被否决者重新定义基准 |

检查适用性须显式表示，不能再把 `null` 同时用于“不适用”“没检查”“检查失败”：

| 调用情境 | 正文保留比较 |
| --- | --- |
| 首次创作的首个候选 | 没有修复前版本，标为不适用；可通过其他门禁，不声称已完成保留比较 |
| 用户主动修改的首个候选 | 新用户回合允许语义变化；不拿旧成品禁止用户改日期/删电话；建立本回合新的修复基准 |
| 同一回合的自动修复候选 | 必须对照冻结基准；缺基准/投影失败为明确阻断或无法验收，不能自动提升 |
| 单项素材重试、确定性排版修复 | 没有新的正文修改授权，必须保留现有正文事实 |

情境来自实际调用入口和修复轮次，不从用户句子关键词推断。此处保证的是**自动修复不破坏已存在的事实**，不夸大为“首稿已完整理解用户所有要求”。

### 4.3 建立可信正文投影和规范事实

优先复用 compose 已有解析/emit 元信息得到正文单元及来源位置。包括作者标题、正文、列表、引用和照片说明；排除内部素材协议、SVG 属性、样式数字及系统生成的拒收提示。合法技术代码示例和泄漏的内部 SVG 必须区分。

不能直接把 raw v2 喂给事实抽取：viewBox、坐标、素材 ID 都会被当成事实。也不能将 HTML 折为一行后继续套源文行号 `ignore`。源文节点范围、正文单元范围与显示文本须保留对应关系。

两侧抽取有类型的事实 token，包含规范值、原始显示、来源范围；按规范值和合理的出现/来源约束匹配，避免裸字符串包含判断。明确支持的规范化至少覆盖：

- `8 点 30 分`、`08:30`、`8:30` 的同一时间表达；`18:30` 必须是不同事实。
- 电话的空格/连字符展示差异可规范，数字不得增加、删除或因前缀包含关系混同。
- `负责接待的是张老师` 与 `张老师负责接待` 保留同一姓名；不能把“责接待的是张老师”整个片段当姓名。
- 日期空白与书写格式可规范，不丢年份；人数、金额等数字保留单位含义。
- 同一问题行包含 emoji 和日期时，修复 emoji 的许可不豁免该行日期。正文片段提示与事实豁免分别处理。

实现应声明可支持的规范化边界，不把宽泛“语义差不多”当作自动豁免。比较所必需的事实无法可靠提取时明确无法验收，不能静默当作没有事实。

按既有已确认口径统一结果：普通片段删改为 warning，事实缺失为 blocking。`body.ok`、问题列表、`gate.bodyIntegrityOk`、总 `verdict.ok` 和 UI 结果必须一致；没有相应阻断证据时不能留下隐藏的 false。

### 4.4 候选处理的固定顺序

1. 解析、素材处理、渲染，形成同一轮 source/HTML/绑定/快照与不可变诊断。
2. 核对取消、当前 runId、文档身份和提交基准；每个异步返回都防止迟到覆盖。
3. 根据检查上下文执行正文保留和其他全部门禁。
4. 比较新增阻断、事实变化与其他退化。末轮也执行，不能先被 `atCap` 跳过。
5. 否决候选只进入失败草稿/诊断，不更新 `best`、事实基准、可提交预览或成品指针。
6. 可采纳者才能参与选择。提交以完整 `verdict.ok` 和所需检查完成为前提，不只看 `blockers.length===0`。
7. 仍有问题，再判断不可修复、无进展或预算耗尽；允许下一次修复时保持原素材台账和预算。

“无进展”同时比较稳定问题指纹和候选内容指纹。当前 `sameCodes` 仅比较代码列表，却在日志声称产物未变，需校正。同类问题仍存在但内容确有进展时不能提前当作空转。

修订提示可以携带保护事实帮助模型，但验收仍由确定性检查完成。确保 `buildReviseContent` 接收到提取后的单一 v2 源文，避免把含围栏的完整助手回复再次包进 v2，造成嵌套围栏。

### 4.5 B 包必测

| 用例 | 期望 |
| --- | --- |
| 首稿合格 | 正常提交；首稿保留比较不适用 |
| 句中 emoji/独立一行 emoji 被删除，事实保留 | 自动修复可通过，不被隐藏布尔值卡住 |
| 逐一删除日期、时间、地点、姓名、人数 | 明确定位缺失；不得成为成品 |
| `8:30→18:30`、电话尾部追加一位 | 阻断；正反对照排除 substring 漏检 |
| 同义时间格式、姓名句式调整 | 通过，不把虚词当保护事实 |
| 当前用户回合主动改日期/删电话 | 首个候选不被旧版本误杀；自动修复保护新事实 |
| 只改样式、SVG 坐标、素材实现 | 不把这些数字视为正文事实；正文保持 |
| 两轮修复逐步丢事实 | 第二轮仍被首稿冻结基准发现 |
| 原问题减少但新增事实阻断，发生在最后一轮 | 不能因总数下降、预算结束或提前 best 而提交 |

| 有/无旧成品两种失败情况 | 分别为完整恢复/草稿未通过，不制造不存在的回滚 |
| 单项素材重试 | 正文比较仍生效，已有素材预算不被重置 |

至少两项打到当前 App：丢事实组不可 accepted；保留事实及独立 emoji 组可 accepted。只测纯函数不足以关闭 F1。

## 5. 包 C：准备阶段契约与真实续改

### 5.1 两条失败路径必须一起关闭

F2 的响应是 `需要的信息已齐备，这就不再多问，进入撰写。\n\nREADY`（实际是换行）。`prep.ts:isReadinessMarker` 仅认全文相等；`runPrep` 将其返回为 `ready:false`，`App.tsx:722–735` 提前结束。

F3 的完整响应见夹具 `prep.messages` 最后一条，包含新标题和完整 v2 稿件。它同样被 `ready:false` 分支接收，只调用 `updateAssistant` 和 `persistNow` 保存聊天；没有进入统一交付。准备阶段的 trace 为两次 prep，无正文提交，成品仍是原 revision。

因此不能只改为 `text.includes('READY')`：这覆盖不了 F3，还会误认普通答疑、引用的 READY、NOT READY。

### 5.2 推荐契约：模型选择结果，程序验证并执行

建议复用现有已经实测可用的 function-calling 通道，增加终结准备阶段的工具。示意结构，不要求逐字使用此命名：

```ts
finish_preparation({
  outcome: 'reply' | 'compose' | 'candidate',
  text?: string,           // reply 的普通答复/澄清
  source?: string,         // candidate 的单一完整 v2 源文
  baseRevisionId?: string,
  assetPolicy?: 'preserve' | 'modify'
})
```

- `reply`：模型选择普通答复或澄清；不调用正文生成、不提交文稿。
- `compose`：模型明确选择写作；带知识摘要和当前正式源文执行一次正文请求，再进统一交付。
- `candidate`：模型已经给出完整稿件；直接走统一交付，不再花一次请求重写同稿。
- `assetPolicy` 表达模型选定的本回合素材操作，不能由前端中文关键词填充。应用在回合开始捕获的文档 ID、revision/generation 才是权威提交基准；模型的 `baseRevisionId` 最多用于一致性回显，缺失或不同不能替换应用基准、移向新版本或绕过 CAS。

内部使用可判别联合类型表示结果，替换含义混杂的 `ready?:boolean + text?:string`。校验必需字段、互斥字段、空 source、未知 enum、冲突终结工具与版本身份。

建议一份响应只允许“若干知识工具”或“一次终结工具”；两者混用或多个终结视为协议错误，不能抢先提交。保留每个 tool_call_id 对应结果，重复读取可复用本回合缓存。

沿用当前服务已使用的工具格式。不要假定供应商支持额外的 strict JSON Schema、特定 tool_choice 或新接口协议，也不要为本修复改锁定模型。

### 5.3 兼容及异常行为

| 响应/异常 | 处理 |
| --- | --- |
| 合法终结工具 | 按模型声明机械执行 |
| 旧版纯 READY | 新协议下视为待确认结果，在剩余预算内要求模型给出终结契约；只有当前调用已具备明确的创作操作契约时才允许受测的兼容转换 |
| 一个完整且唯一的旧 v2 稿件 | 可以提取源文但不能仅凭围栏推导提交意图；确认模型 outcome/素材策略后，保留原正文进入同一交付流程，不要求重新生成整稿 |
| 说明 + READY，或只有“已改好”但没有合法结果 | 最多一次协议纠偏，请模型表达结构化结果；不能当澄清成功、不能猜成 compose |
| 多份/不闭合 v2、终结参数非法或相互冲突 | 协议错误或有界纠偏，不从多个稿件中静默挑一个 |
| 空内容、截断、网络/鉴权错误、取消、轮数耗尽 | 分类报告，保留旧成品，不自动获得写作授权 |

兼容候选也必须验证其素材编辑权限；不能因为识别到围栏，就绕过只改文字时的素材保护。“只回复 READY”或询问 v2 语法示例仍可能只是普通答疑，必须由模型的合法终结结果决定 reply，而不是由产物词语/围栏决定写作。协议版本和已成立的本回合操作契约须显式传入，不能靠历史创作关键词推测。

当前 `runPrep` 耗尽后 `ready:true` 和 App catch 后 `ready:true` 都会把错误转换成创作，需改为明确失败/取消/协议结果。网络或取消异常不能走协议纠偏重试。

建议保留总 `MAX_PREP_CALLS=3`，协议纠偏最多 1 次且**占用同一总额**；知识后续、空响应重试和纠偏不各自拥有三次。不能为了两条夹具放大正常请求数。第三次后仍未得到合法终结结果才按耗尽失败；第三次合法返回 compose/candidate 时仍执行该结果，但不得追加第四次准备请求。

生产入口应让模型获得决定 reply/compose/candidate 的工具能力，不依赖 `isCreateRequest` 或历史创作词才能进入契约。可让每个桌面回合走统一模型入口：普通问答直接以 reply 结束，同一回合不再额外调用 WRITE。浏览器 mock 的简化规则限于测试环境。新增流转是执行模型结果，不能演变成前端对话状态机。

重建 prep 最后用户消息时保留已有 `images` 等字段；当前 `prep.ts` 重组消息只保留 role/content。这一检查只证明传参，不等于验证真实图像理解。

### 5.4 统一交付入口与当前文稿上下文

将“主写作流结束后”的候选处理提取成公共入口，接收明确的 runId、当前文档身份、原始回复、单一源文、当前正式版本与台账。主写作、prep 直接候选、自动修复必须进入同一门禁，不能各写一份相似逻辑。

在本回合调用模型**之前**读取当前正式文稿，而不是等写作结束才读取。向模型提供明确标注的实际保存上下文：revisionId、canonical source、素材稳定引用和必要绑定信息。历史助手 raw reply 仅是历史消息，不是最新成品。

读取失败明确报错；不能当作“没有旧稿”继续覆盖。沿用已有未验证 legacy 版本语义，不能因打开了旧文档就补造验收记录。

当前真实样例的正式源文已有：

```text
[[asset:art-wide|as-1790663783921024000|横幅插画：暖色台灯照亮桌面上一本蓝色书本，暖黄光线，低饱和蓝与暖橙配色，画面无任何文字]]
```

而历史助手正文及 F3 返回稿仍有同一素材的 `[[img:wide|...|new]]`。本轮编辑选择 `assetPolicy=preserve` 时，应在派发绘图前拦截这种身份退化：

1. 优先让模型基于 canonical source 保持 `[[asset:...]]`。
2. 如做确定性恢复，只允许依据当前文档确切 slot/绑定/历史占位来源，将已知旧占位恢复为同一 assetId/快照。不能按模糊描述随便选库素材。
3. 无法唯一对应时，明确阻断/在剩余协议预算内归一化；不能当新料偷偷绘制。
4. 模型根据用户要求明确选择修改/新建素材的回合仍可走受限新绘制；不得全局剥掉 `|new` 或永远强制复用。

素材保护依赖当前操作契约和事实绑定，不扫描用户句子里的“不要画/只改文字”来控制对话。

### 5.5 完成状态绑定本轮提交

只有统一门禁通过、存储返回成功、读回对应文档的 revision/runId 与本轮一致，才能标记本轮已保存。保存失败、CAS 冲突、取消或协议失败时，旧稿仍可显示，但不能用旧稿 accepted 证明本轮更新。

普通答复继续显示旧稿时，用已有状态区域清楚表明没有发生本轮文稿提交；不要另加一堆调试小字。准备提示词禁止将计划或生成结果描述为“已保存”。应用完成提示只从提交回执生成，不靠搜索“已改好”等中文语句判断。

trace 补齐准备结果类型、协议纠偏次数、失败分类、候选来源、正文比较是否适用/完成、commit/rollback、revisionId。prep 请求也保留 finish_reason/usage（服务提供时）；不能漏记后猜费用。既有日志脱敏与容量上限保持。

## 6. 包 D：中间预览与外链样例

根因路径：`App.tsx:updateAssistant` 在最终门禁前 `setHtml`；`PreviewPane` 以 `wrapSrcDoc(html)` 放入 iframe。现有 iframe sandbox 并未阻止本轮外链图片请求。

在**所有候选进入预览的公共边界**抑制禁止的外部资源加载，包括主流式、prep 直接候选、修订流、素材异步渲染和文档打开路径。可以采用预览专用资源清理/占位与明确的资源策略；若采用 CSP，验证现有内联样式、data/blob 图、点选组件与导出均不受误伤。

必须分开：

- 原始候选 source/HTML：保留违规外链，供质量检查、失败草稿和诊断使用。
- 实时显示版本：不得发起禁止的 HTTP(S) 资源请求，可以显示稳定占位。
- 合格正式版本：经过统一门禁才用于成品及导出。

不能先清空原始外链，再对清空结果检查而声称问题不存在。也不能关闭所有图片或吞掉 console error 来让 S2 变绿。

将现有测试拆成两项：

1. **S2 交付检查**：可为精确测试 URL 提供本地固定响应，消除公网依赖；仍保留外链源文和问题码，验证最终修复后的 source/HTML/成品一致。不把 fixture 改成 data 图片绕过外链规则。
2. **全过程资源检查**：从发送前开始记录所有预览资源请求，包括重试、redirect、srcset/CSS 等实际支持入口；未经许可的外链尝试必须为 0。测试 route 只是防意外联网并计数，不能因为它阻止请求就把产品标为通过。

修复前 S2 最终成品合格与中间请求失败同时成立；修复后两项分别验收。纯测试环境错误和产品预览行为分别报告。

5. 检查 PID、启动时间、exe 哈希、端口所属进程树、WebView `--user-data-dir`、CDP Tauri 页面与预期空会话/文稿状态，全部匹配后才派发付费请求。
6. 同一 profile 只允许一个实例。本轮曾因首次受限实例未退出而使后续实例没有可用 CDP；不能启动第二个后就假定连通。只清理本轮确切拥有的进程，不按进程名杀掉用户实例。
7. 等待真实就绪用条件和有限超时，不能只 sleep 后宣称成功。取消或基础设施失败记录 BLOCKED/FAIL，不冒充业务成功。

### 7.4 最小真实验收集

| 场景 | 成功必须同时满足 |
| --- | --- |
| L1 空库首篇 | 短通知事实完整，1 个要求的素材位实际落位；入库、绑定、快照和同轮提交一致；绘图在既有预算内，重试计数实报 |
| L2 同会话只改文字 | 标题节点确为“周末到馆提醒”；正文≤180 字；完整开放/闭馆信息及电话保留；source 与 revision 实变；新 revision/runId 属于本轮；gen_svg=0；素材身份/版本/快照不变 |
| L3 继续/普通答疑或取消，按剩余额度选择 | 有稿时不会误写；若再次修改则真的提交，若答疑/取消则无提交；不把旧稿绿色条当成功 |
| L4 关闭重开，不新增模型请求 | 记录最后一次成功提交；正常关停自有 PID 后启动新 PID；读回 source/HTML/revision/绑定/快照/哈希与关停前最后成功版相同 |
| L5 从当前成品导出，不新增模型请求 | UI 明确成功；本次新建 HTML 与当前成品一致；长图及分页 PNG 可解码、宽 750px、内容完整；截图/人工查看留证 |

L2 的事实按完整语义核对：10月10日周六 9:00–17:00 开放；10月11日周日全天闭馆；自习区一楼；电话 010-55556666。不要只断言正文含 `10月11日` 而漏掉“全天闭馆”。字数口径预先固定为可见正文（标题及图像替代说明是否计入明确记录），禁止在失败后改口径。

正式文档的侧栏名称当前可能来自会话标题，不等于文章标题。验收修改标题应检查源文标题及预览标题节点，不要求无关的会话名同步变化。

L4 必须比较**关闭前最后成功提交**，不是永远与 L1 比；本轮旧测试能与 L1 相等，只因为两次续改都失败。L5 记录导出前清单，验证本轮新增文件，不能让旧 exports 文件使本次失败通过。

本轮真实参考值：首篇 133.384 秒、写作 35.228 秒、绘图 90.865 秒；3 回合共 8 条 request 记录、1 次绘图。它们是历史证据，不是性能 SLA。request 记录数不等于完整计费账单，usage 缺失时费用未知。

### 7.5 收尾

保存原始日志和脱敏业务文件，重新核对真实工作区全文件哈希，关闭本轮自有程序及开发服务。临时目录删除前解析完整路径，确认属于本次唯一测试根；在同一 PowerShell 中使用 LiteralPath 操作，不能跨 shell 拼接删除命令。保留脱敏证据，清理临时凭据和运行 profile。

本轮 `live-create/live-revise` 是读取原始产物后的业务判定；当时 runner 的退出码只说明链路结束。`live-continue` 才加入更强断言。新 runner 每例保存自己的版本/哈希，不能用后来脚本的逻辑追认先前运行时已经做了相同检查。
