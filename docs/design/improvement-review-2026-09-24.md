## 1. 第二篇不生成新素材：复用策略会吞掉新需求

**已验证，优先修复。** [image-agent.ts](../../src/lib/image-agent.ts) 的 candidatesFor/scoreOf/materializePlaceholders（84、91、166–184 行），与 [asset-library.ts](../../src/lib/asset-library.ts) 的 searchAssets（283 行）共同决定复用。

实际机制：第一篇生成后自动入库；下一篇先检索，描述只要共享 3 个字符二元组就可能被判为“强命中”。这个门槛没有按描述长度归一化，没有主体/颜色/用途冲突否决，也没有强制新建选项。风格只是加分项。查找先截取前 10 项，再由调用方筛分类，还可能漏掉真正适合的候选。

隔离输入与结果：

| 输入 | gen_svg 调用 | 结果 |
| --- | --- | --- |
| 空库：右下角一朵红色玫瑰花，校园毕业季 | 1 | 生成并入库 |
| 同一库：右下角一朵蓝色雪花，冬季科技大会 | 0 | 复用上一张玫瑰素材 |
| 描述前加“必须重新绘制全新素材” | 0 | 仍被复用分支截获 |

因此，现象不一定是模型拒绝画图：请求可能根本没到生成模型。尚不能证明用户实际文章恰好经过同一分支；同会话沿用旧稿也可能同时存在。

**修改建议：** 素材请求明确携带“自动选择 / 复用指定素材 / 必须新建”策略；用户说重新设计时必须贯穿主模型、工具和解析器。先按角色、比例、占位筛选，再做文字候选检索；主体、场景、配色冲突时否决复用。文字相似只用于找候选，不能直接替代最终选择。记录每个素材位为什么复用或新建，允许用户只重做这一项。

**验收：** 上述不同主体案例必须产生新调用；显式复用必须零生成；强制新建不能命中旧库。不要以“每篇必须全部重画”替代合理复用。

## 2. 角饰复用存在确定的引用错误

**已验证，优先修复。** [image-agent.ts](../../src/lib/image-agent.ts) 的 svgBlock（105 行）按库 ID 输出角饰定义；传统占位命中后（174 行附近）直接替换，而正文中的原角饰别名未同步。

隔离案例中，定义变成 `::: art deco asset-1`，气泡仍引用 `> [!KEY|second]`；调用真实 compose 后返回“气泡角饰 second 未定义”。这会引发自动重写，给用户的表现可能是小框没装饰、重复修订或素材不稳定。

另外，显式引用虽然解析了分类，但查找只用 ID/name，不校验分类；把已有 deco 用 art-wide 分类引用，仍成功输出 deco，隔离验证已确认。

**修改建议：** 分开保存“素材库身份”和“本文素材位别名”，解析时保留别名或统一更新引用；校验声明分类、实际分类和使用位置。已命中素材的确定性引用问题，应由解析器处理，不能交给模型重写整篇。

**验收：** 新画、跨篇复用、改名和版本更新后角饰都能定位；错分类返回可解释错误；该场景不触发全文自动修订。

## 3. 小素材质量差：分类、提示词、实际尺寸和质检均不匹配

**源码确认 + 校验缺陷已验证。** [chat.rs](../../src-tauri/src/chat.rs) 的 SVG_SYSTEM_PROMPT（215 行）统一要求插画式空间、体积、细节密度，小图也要求不少于 10 个元素；deco 又要求主体集中在 300×300 画布的右下 1/3（233 行）。[compose.ts](../../src/lib/compose.ts) 将整个角饰以 60px 宽显示（255 行），按该布局主体线性尺度约 20px，丰富细节容易在最终尺寸下失去可读性。气泡文字也没有专门为角饰预留避让区域。

[asset-agent.ts](../../src/lib/asset-agent.ts) 的 kindForCategory（13 行）把 bubble/deco 合并，把 photo-frame 与 banner/art-wide 都变为 wide；照片框缺少专门的透明中窗、边缘、安全区要求。

必须区分用户说的“小框”：

- 气泡框本体：由 compose 的 bubble 固定 HTML/CSS 生成，素材模型只画角饰。
- 正文 frame 容器：由 frameBlock（367 行）固定边线绘制。
- 素材库 photo-frame：走 wide 插画模型提示。

所以仅升级 SVG 模型不能同时改善三类框。

当前生成校验主要看 viewBox 和元素数≥6（asset-agent.ts:31、image-agent.ts:233）。隔离样例中，六个位于画布外、fill=none 的圆也被接受；没有像素可见性或视觉质量判断。

**修改建议：** 保留大图有效的绘制方式；为角饰、分隔线、照片框分别建立适配角色的要求。小角饰看轮廓、占画布比例、缩小后辨识度与文字避让，不以堆元素为目标。照片框明确中间透明区域与边框宽度；容器本体改善间距、边线、字体层级。质检先检查渲染非空/越界/透明与占位，再在实际显示尺寸下做视觉判断。

**验收：** 同时检查原图、60px 实际显示及含文字的小框截图；空白 SVG、遮字、主体缩得不可辨均不得通过；大图质量不得因统一“简化”而退化。

## 4. 模型分不清素材：它现在看不到素材的样子

**源码确认。** [prep.ts](../../src/lib/prep.ts) 的 runPrepTool（58 行附近）只返回分类、名称、标题、描述、usage、style、version。入库 desc 又主要沿用用户请求（asset-agent.ts:77、image-agent.ts 的 addAsset），没有验证实际画面是否符合描述。

主模型据文字选素材，检索器也据文字选素材；如果“描述说是花、实际画得像叶子”，两层都没有观察真实图像的机会。类别按用途合并、显式引用不校验分类，会进一步放大错配。

**修改建议：** 素材元数据同时保留“原需求”和“实际画面描述”，增加角色、主体、比例、透明区、适用尺寸等字段。先低成本文字召回，再让视觉模型查看少量候选缩略图和目标位置，给出复用/新建决定与原因。新素材渲染后再生成实际描述；不要把模型自称完成当作看图验收。

## 5. 回答生硬：提示词之外还有前端启发式和统一排版配额

**源码确认，体验影响待真实模型验证。** [persona.ts](../../src/lib/persona.ts) 第 13–20 行列出多项必澄清维度，并默认 1500–2500 字。[App.tsx](../../src/App.tsx) 的 needPrep（330 行）由创作关键词或上一条助手包含中文问号决定；creativeSession（334 行）检查历史任一创作请求。并非前端对话状态机，但这些启发式实际影响工具入口，与“全部由模型理解”的目标存在偏差。

[compose.ts](../../src/lib/compose.ts) 第 789–805 行对文章统一要求素材数量、至少两个容器、一个气泡及列表/引用；[revise.ts](../../src/lib/revise.ts) 又据此触发最多两次全文重写。简短通知、克制排版也可能被推向相同模板。[App.tsx](../../src/App.tsx) 第 478 行附近重写时清空旧预览，放大等待和不确定感。主文本请求还固定 reasoning_effort=max、max_tokens=64000（chat.rs:159）；不能据此断言实际消耗，但应检查是否适合所有回合。

**修改建议：** 由模型区分闲聊、澄清、修改与新稿，统一提供可用工具；不要再用问号决定是否能取知识。保留“重要事实不臆造、未授权不擅自定关键需求”的原要求，但每次只问真正阻碍成稿的少数问题，复用已知信息，并提供明确授权默认的操作。按文章类型、长度和用户偏好制定质量标准；短通知不强塞素材和组件。局部问题局部修订，保留上一版预览；按任务配置推理/输出预算，先测效果再选默认。

## 8. 利用 V4.1 Flash 多模态：先接通观察，再改决策

用户指定以 DeepSeek V4.1 Flash 为目标模型。源码默认字符串仍是 deepseek-v4-flash（settings.ts:17、chat.rs:103）；不能据此断定服务端仍是旧模型。官方 2026-09-10 发布说明称，正式接口名为 deepseek-flash，旧 deepseek-v4-flash 暂时路由至 V4.1 Flash。自定义服务商的名称需单独核验，本轮未读取本机密钥、环境变量或发送实际请求。[官方发布说明](https://api-docs.deepseek.com/news/news260910/)

素材生成有独立 image_model 配置，源码回退 deepseek-chat（chat.rs:270），不随设置面板的主模型自动改变；该名称当前最终映射及效果本轮未测，不能直接认定是某个旧版本。

接入障碍明确：前端 ChatMsg.content 是 string|null，Rust ChatMsg.content 是 Option<String>，没有图片内容块；聊天框也没有图片附件入口。官方 Chat Completions 图像输入使用 user 消息的 content 数组，支持图像块；SVG 应先渲染为 PNG 等受支持格式。现有 SVG→PNG 路径可作为基础，但不是已经接通多模态。[官方视觉指南](https://api-docs.deepseek.com/guides/vision/)

建议按收益顺序使用视觉能力：

1. **选素材看实图**：只对筛选后的少量候选看图，核对主体、颜色、角色与目标位置；有明确差异就新建。
2. **小组件看最终效果**：将角饰嵌入真实文字框后截取局部截图，同时提供实际尺寸和原图；让模型指出遮挡、辨识度、留白与主题问题，最多一次定向修订。
3. **支持用户参考图**：上传素材或版式参考，提取可复用的设计特征及用户指定保留部分，再指导内容和 SVG 生成。
4. **整稿最后检查**：按需审阅手机尺度截图，修具体组件，避免每次对话都上传整篇长图。

多模态输入是看图与理解能力，不等于直接输出位图；现有 SVG 生成路线可保留。第一阶段可继续 Chat Completions，不必为此全面迁移 API。

费用控制：缩略候选先筛选、按素材版本缓存视觉描述、一次只看相关局部；视觉复核只在新生成/变更/低置信匹配时触发，设置调用上限，失败回退并显示原因。先用离线确定性检查挡住空白、越界等错误，再花模型费用。
