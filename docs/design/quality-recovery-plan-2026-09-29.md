# 最新推文源码泄漏与自动修复、回滚修改方案

日期：2026-09-29。状态：**A–E 五批已实施，离线/浏览器/构建验证通过，待用户验收**。

> **实施结果与两处口径裁决**（2026-09-29 收尾时补记，详见 [PROGRESS](../../PROGRESS.md)）：
> 1. **§5 第 3 条按字面执行**：「无阻断项 → 进入持久化提交；有阻断项 → 生成修复任务」。
>    因此**提示级问题不再触发整篇重写**——组件数量不足之类只作提示（§4 也明列"不强迫改稿"）。
>    这取代了旧行为（按中文子串 `FIXABLE_KEYS` 匹配就推回模型重写），后者既用展示文案控制执行，
>    又会为少几条告警把一篇合格稿子整篇换成另一篇（实测：引用库素材的稿子被换成不带库引用的版本，
>    文档固化快照随之清空）。受影响的 E2E 断言（S2/S10）已按新契约重写，**不是**放宽而是换判据。
> 2. **§4 的"素材被拒收"与"正文片段丢失"分级**：素材拒收 → 阻断（`asset.rejected`）；
>    **正文片段丢失降为提示**（`body.text-lost` 不再是阻断项），**事实丢失仍阻断**（`body.fact-lost`）。
>    理由是 §5.6 的两句必须同时成立——"无关段落变化要撤销候选"与"不能将'与旧稿不同'一律当退化"；
>    而本模块做的是全文纯文本比较，**没有节点级的"目标/非目标"划分**，无法区分"这段是修复要删的"
>    与"这段是被误伤的"。实测后果：违规稿里那段 emoji 被重写掉后，完整性检查报阻断 → 候选被撤销
>    → **修复永远无法生效**。折中口径已在 `src/lib/delivery-quality.ts` 的 `issuesFromBody` 里写明。

目标：修复照片位吞并素材导致的前端异常文字，并将质量检查接入自动修复、复检和完整版本回滚。失败候选可保存用于继续编辑，但不能自动替换已验收成品。

## 3. 照片位和块解析修复

### 3.1 确定协议，不能只让模型补结束符

正式生成写法继续采用现有知识约定：`::: photo 照片说明` 是单行指令，正文从下一行开始。主模型和自动修订提示保持一致。

历史多行照片块通过显式兼容逻辑读取：先验证候选范围内存在结束符，且没有其他块起点、标题、素材指令、气泡、列表或空行形成的正文边界，再将其识别为旧照片块。不能无界扫描到下一个任意 `:::`。

历史输入无法无歧义识别时，保留原文，按单行照片位解析；其余行作为正文或独立节点处理，并返回兼容性提示。不能静默吞掉正文。旧格式专用迁移只对隔离副本进行，不能覆写用户原稿。

### 3.2 解析产物保留来源

- 解析节点至少携带节点类型、源文行范围和素材 slotId/assetId；起止标记必须属于同一块。
- 本次先抽出有边界的块收集函数，覆盖 photo/art/card/steps 等实际扫描入口；不要求一次性重写整个排版器。
- 渲染返回节点到 HTML/素材的映射，后续检查可精确定位问题，不能靠从展示文案反推素材身份。
- 检查可见文本是否泄漏内部 `::: art`、转义 SVG、未解析素材指令或失败占位。仅检查不允许出现协议的正文节点，合法代码示例不能被全局字符串规则误杀。
- 本次异常先走解析器确定性修复，不让模型反复重写文章来补偿程序错误。

## 4. 统一质量结果和交付门禁

建议增加 `src/lib/delivery-quality.ts`，统一汇总解析、素材、栅格、HTML 和正文完整性检查。现有检查可以保留为底层函数。

每条问题使用稳定字段：`code`、`severity`（blocking/warning/info）、`stage`、`message`、`sourceRange`、可选 `nodeId/slotId/assetId`、`repairKind` 和证据摘要。中文文案只负责展示，不作为分支条件。

候选记录至少包含：`runId`、`attempt`、`baseRevisionId`、`source`、`normalizedSource`、`html`、`bindings`、`snapshots`、`issues` 和 `validationVersion`。所有字段来自同一轮候选。

| 问题 | 默认处理 | 修复策略 |
| --- | --- | --- |
| 内部源码泄漏、跨块吞并、正文非预期丢失 | 阻断成品提升 | 修正解析/局部结构后重新渲染 |
| 必需素材被拒收、渲染失败、引用不匹配 | 阻断成品提升 | 恢复对应已验收快照，或替换/重绘该素材位 |
| 当前产品规范禁止的字符或样式 | 阻断成品提升 | 可证明语义不变时局部规范化，否则定点修订 |
| 平台容量约束 | 按已验证的目标格式规则判定 | 先清除泄漏、核实度量阶段，再考虑压缩；不能直接删正文凑长度 |
| 有意短篇、推荐性组件数量 | 提示 | 不强迫改稿，不阻断成品 |
| 照片位等待用户真实照片 | 明示待补照片 | 创作草稿允许；发布就绪检查单独判定，不自动伪造照片 |

交付规则：阻断项为 0、必需素材完成、正文完整性通过、版本字段一致，才允许提交成品。`checkHtml.ok` 单独为真不等于整稿通过；磁盘保存成功也不等于验收通过。

“20000 字符”现有规则须核对计算对象：源文、渲染 HTML、内嵌图片数据与实际发布格式不是同一尺寸。先登记为明确的长度风险；未验证前，不把旧警告当作已验证的平台拒绝事实，也不擅自移除保护。

## 5. 自动修复和复检流程

1. 创建候选，记录本轮基准成品版本；不覆盖上一份成品。
2. 解析、素材处理、渲染后汇总全部质量结果。
3. 无阻断项：进入持久化提交；有阻断项：按问题类型生成修复任务。
4. 优先执行确定性局部修复，然后对失败素材做局部恢复/替换，最后才调用主模型修订必要文本。
5. 每轮修复后重新渲染并跑完整门禁；不仅复查原问题，还检查新增问题和正文保留。
6. 修复候选出现新增阻断项、无关段落变化或事实内容丢失时，撤销该候选并保留诊断；不得以告警总数减少掩盖更严重退化。
7. 修复预算用尽、取消、无进展或不可修复时：保存失败草稿及诊断，成品维持上一份已验收版本。没有合格历史时显示“草稿未通过”，不制造回滚成功结论。

预算建议：沿用最多两轮主文自动修订；同一素材位沿用现有最多两次绘图预算和累计超时，不因全文修订、复检、故障重试而重置。确定性修复不产生模型调用。遇到相同问题指纹且产物未变化时提前结束，避免空转。

绘图质检失败的第二次尝试应携带具体失败原因和必要上下文，而不是原描述盲重试。鉴权、参数、库读取失败不能被重写或重画掩盖。不能为了清空问题清单，静默删除用户明确要求的素材或正文。

正文保护：对目标以外节点做文本/顺序比较，保护已有姓名、时间、地点、数字等事实。全篇结构修改只有在当前用户请求需要时允许；不能将“与旧稿不同”一律当退化，也不能将模型承诺“保留了”当证据。

这些状态描述产物执行和验收，不用于控制用户意图、澄清或对话路由，遵守项目禁止前端对话状态机的约束。

## 6. 素材完成状态贯通

- 库读取成功仅代表素材可读；结构、实际尺寸栅格、最终落位通过后才可记为验收完成。
- 复用素材与新生成素材执行一致的适用门禁；按资产版本、用途、渲染尺寸和检查版本缓存结果，不能每轮重复昂贵操作。
- `compose`/渲染器必须返回失败素材的 slotId，回写台账和候选问题清单。已经被照片位吞掉、未实际落位的素材也不能被算作交付成功。
- 恢复素材优先使用本文同一素材位的已验收快照，并核实与当前需求兼容；不能自动恢复另一个主题的旧图。
- 单项重试后仍走整稿门禁与版本提交，不能通过独立保存入口绕过检查。
- 用户手动重试作为显式新尝试记录；自动流程不得冒充用户重试来重置预算。

## 7. 完整版本与可靠回滚

### 7.1 建议存储结构

```text
documents/<docId>/
  manifest.json                 # schemaVersion、acceptedRevisionId、draftRevisionId、generation
  revisions/<revisionId>/
    source.md
    article.html
    meta.json                   # 绑定、快照、诊断、检查版本、文件哈希和来源 runId
  staging/<transactionId>/      # 未提交候选，读者不可当成当前成品
```

同一份版本必须完整绑定源文、HTML、素材快照、绑定和质量结果。草稿与成品可以指向不同版本，但 UI 和导出必须明确使用哪个版本。

### 7.2 提交与故障恢复

1. 写入临时版本，检查全部必要文件、哈希、绑定和质量记录。
2. 完成文件写入和必要同步后，将候选安装为不可变版本。
3. 以 Windows 支持的可靠替换方式提交 manifest；实现时验证替换失败和崩溃边界，不能假设多个 `write` 或跨文件重命名构成事务。
4. 检查提交前的 generation/baseRevisionId，旧请求不能覆盖用户较新的提交。
5. 提交失败时旧指针保持有效，返回明确错误；不能先删旧文件再尝试提交。
6. 重开应用时只读取已提交完整版本；孤立 staging/版本保留供恢复或诊断，不自动提升为成品。首批实现不自动清理历史版本。

回滚通过选择完整已验收版本实现，不拼接旧 HTML 和新元数据。自动失败恢复不应丢掉最新草稿；用户仍可继续修订该草稿。取消、切换会话、迟到响应均需要 runId 和文档版本校验，不能提交到错误会话。

### 7.3 旧文档迁移

当前三文件原件先保留并校验，再复制为 legacy 版本。旧版本没有验收记录，默认标为“未验证”，不能因为有图片就成为合格回滚目标。检查失败则保留为草稿。读取失败明确报错，不得按“没有旧稿”继续覆盖。

旧格式兼容读取持续保留；迁移失败时原文档仍可恢复。所有故障注入在临时工作区进行，不对真实文档做破坏性测试。

## 8. 前端和日志行为

- `PreviewPane` 汇总同一份质量结果，区分“修复中”“草稿未通过”“已恢复上一版成品”“成品已验收并保存”。
- 预览明确标识显示的是草稿还是成品；最新聊天内容不能被误解为已经更新了正式成品。
- 正常导出入口使用已验收成品；失败候选允许通过明确标注的草稿导出入口取回，不静默作为成品交付。
- 日志拆分 `validation / repair / rollback / persist / commit`，记录候选版本、问题代码、前后结果、耗时和停止原因。保存诊断草稿记为持久化成功，但交付仍失败。
- 不记录密钥或无必要的全文；与现有 runId/slotId 追踪兼容。

## 10. 必须覆盖的验收场景

| 场景 | 可证伪的验收断言 |
| --- | --- |
| 当前最新稿隔离副本 | 3 个照片位后续内容保留；可见文本无转义 SVG/内部 art；所有预期素材落位或明确阻断 |
| 单行照片位接 art/card/标题/气泡/列表/另一个 photo | 后续节点不被吞并，源文范围不跨块 |
| 历史闭合照片块与缺失结束符 | 合法旧块兼容；歧义输入不吞正文、不静默删除 |
| 库素材读取成功但含禁用 text | 必需 slot 未验收、进入修复或阻断；不得保持全部完成 |
| 有 6 张图仍存在源码泄漏 | 阻断交付，不依赖零图条件 |
| 只有 checkHtml 失败 | 同样进入统一门禁，不能单纯显示红条后提交 |
| 第一轮好、第二轮退化；两轮均失败 | 不接受退化候选；超预算保留草稿和完整旧成品 |
| 没有已验收历史 | 标识未通过，不宣称已回滚、不把 legacy 稿强行认作合格 |
| meta/source/html/manifest 任一步失败 | 当前已提交版本可读；不存在新源文配旧 HTML 的混合版本 |
| 进程中断后重开 | 从最后一次完整提交恢复；未提交候选不成为成品 |
| 取消、切换会话、迟到响应 | 不覆盖新版本、不串文档，不追加超预算请求 |
| 单项重试、打开、导出、素材更新 | 都遵循同一候选门禁和版本绑定，不留旁路 |
| 修复预算与无进展 | 请求计数精确受限；相同失败不会无限重试 |
| 375px 预览和真实显示尺寸素材 | 检查可见文本、节点数量、实际图片与截图，不以 quality-strip 颜色证明整体合格 |

先调用生产模块做离线回归，再用受控服务和临时工作区故障注入；浏览器测试必须断言真实产物与状态。有限真实模型验证须独立记录请求次数、费用范围和实际效果。代码变更验证通过后按项目要求重建 release/NSIS 并启动冒烟，不能结束于 dev 测试。

## 11. 完成判定

只有同时取得解析正确、失败自动修复并复检、修复失败完整恢复、保存重开一致、预算受控和实际预览证据，才能认定本问题闭环完成。静态代码存在、单项质检通过、模型声称修好或日志显示保存成功，都不能替代这些证据。
