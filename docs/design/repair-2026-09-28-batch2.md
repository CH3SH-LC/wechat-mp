# 素材修复（第二批：阶段 4–6）

日期：2026-09-28。第一批（阶段 1–3）见 [同目录记录](repair-2026-09-28-batch1.md)。
本记录保留**决策与口径**；逐文件改动与验证结果见 [详细进度](../../PROGRESS.md)。

第二批解决的是第一批**没有**碰的三件事：等待与调用还会不会放大、素材在实际尺寸下看不看得见、
以及用什么证据确认修好了。

## 一、等待与调用放大（阶段 4）

### 1.1 并发上限 2，但"顺序"由组装阶段保证
绘制阶段改成**两段式**：先逐个素材位做决定（只读本地库，不调模型），再把需要绘制的素材位
交给一个最多 2 个并发的执行器，最后按**正文原始行序**组装。

关键取舍：并发只发生在"绘制"这一段。检索、复用判定、遗留块恢复全部留在决策段顺序执行——
它们都是本地且便宜的，并行只会引入不确定性。**同一描述的素材位共用同一条台账记录**，
于是"相同输入共享在途任务"是台账的**自然结果**，不需要另建一张 in-flight 表：

| 场景 | 结果 |
| --- | --- |
| 同一描述出现两次 | 台账只有 1 条素材位 → 只画 1 次 → 两处都拿到同一个成品块 |
| 三个不同描述 | 并发最多 2 个在跑，但输出顺序与正文一致 |
| 同一描述在下一轮自动修订再出现 | 台账命中成功结论 → 直接复用成品块，0 次绘图 |

### 1.2 超时分三层，且都不"掐死"正常创作
| 层 | 值 | 位置 | 为什么 |
| --- | --- | --- | --- |
| 连接超时 | 15s | Rust（所有请求） | 网络不通时快速失败，不让用户干等 |
| 单次非流式请求 | 180s | Rust（绘图/补描述/prep/视觉复核） | 一次模型调用不该超过这个量级 |
| 单素材位累计 | 240s | 前端（含排队后的执行、重试、补描述） | 一个素材位卡住不该拖垮整篇 |

**流式对话刻意不设总超时**：写一篇长文可能持续数分钟，掐总时长会杀掉正常创作。它只受连接超时约束。

三个值都可用环境变量覆盖（`DEEPSEEK_CONNECT_TIMEOUT` / `DEEPSEEK_NONSTREAM_TIMEOUT` /
`VITE_SLOT_BUDGET_MS`）。这些是**初始参数**，不是实测出来的生成速度——计划原文如此要求。

前端超时用的是"到点即返回"，**不取消底层调用**：底层请求由 Rust 侧 180s 兜底，
它的迟到结果不会再写进台账（写台账的代码已经返回了）。这是刻意的取舍——
强行取消需要跨进程句柄，收益不抵复杂度。

### 1.3 取消：真的让后端停下来，但不夸大承诺
桌面端此前的"停止"只是前端不再显示，请求仍在跑、仍在计费。现在：
- 前端按住停止 → `cancel_run(runId)` 置位该回合的取消信号；
- 所有长耗时调用（流式对话、绘图、补描述、prep、视觉复核）包在 `run_cancellable` 里，
  置位即立刻返回，不等服务端；
- 流式事件**带 runId**：旧回合的迟到增量到前端后被 runId 过滤丢弃，绝不写进新回合草稿；
- 停止后不再派发新素材任务、不再入库（`materializePlaceholders` 的 `cancelled` 回调）。

**必须如实说明的边界**：取消只保证**本地停止等待与后续处理**，不承诺服务端已停止计费。
界面文案同样不宣称"已停止计费"。

实现细节：用 `tokio::sync::watch` 而不是 `Notify`——`watch` 保留当前值，取消**先于**订阅发生时
后到的任务也能立刻看到；`Notify::notify_waiters` 只唤醒当时存在的等待者，会丢掉先到的取消。
另一个坑：`watch::Sender::send` 在**没有接收者**时返回 Err 且**不写入新值**（取消先于调用
正是最常见的情形），必须用 `send_replace`。这两点都有单测钉住。

### 1.4 鉴权类错误不重试；限流按服务端提示等
失败分类里区分两件事（按 HTTP 状态码判，前后端同一口径）：
- **401/403 与 4xx 其余** → `auth`：鉴权/参数错，重试不会改变结果，**不重试**；
- **429 与 5xx** → `network`：限流与暂时性服务端错误，可在剩余预算内重试一次。

`Retry-After` 只在响应头里，而前端拿到的是错误串——沿用与既有 `CLARIFY:` 同一套文本协议，
由 Rust 加 `RETRY_HINT:<秒>` 前缀带过去。前端解析后**只在剩余预算容得下这次等待时才重试**：
等待时间 + 1 秒余量超过剩余预算就直接结束并如实写明原因，而不是把整篇拖超预算。
只认秒数形式；HTTP-date 形式与非法值一律不解析（不猜），上限 10 分钟防止异常值卡死。

### 1.5 自动修订接上 revise 档
此前自动修订走的是默认档（max / 64000），已实现的 high / 32000 修订档没被接上。
现在显式传 `revise`。这是**启用既有旋钮**，不是新增默认值。

## 二、按实际显示尺寸检查素材（阶段 5）

### 2.1 渲染尺寸从"256px 缩略"改成"真实组件宽度"
旧实现一律缩到 256px 再数像素。一张 60px 宽的角饰在 256px 下看起来很饱满，缩到实际尺寸
可能只剩一个几乎看不见的浅色小点——**旧检查天然看不见这个问题**。

现在按该素材位在文章里的真实宽度（角饰 60px、正文插画约 210px、通栏 343px）栅格化 2 倍采样，
再折算回去，得到"主体短边实际有几个像素"。同一枚四叶草角饰在 60px 下量到 32px、在 256px 下
量到 137px——这正是"按真实尺寸检查"的意义。

### 2.2 对比度：主体最清楚的那部分说了算，不是平均值
新增两个指标：墨迹（按 alpha 合成到背景后）与背景的**平均**亮度差，以及**P90** 亮度差。

主判据是 **P90**，不是平均值。原因是实测发现：真实库素材 `star` 有一圈半径 72、几乎全白的
氛围光斑，把平均对比度拉到 12.5——按平均值判会把它误判成"看不见"，而它的主体其实很清楚
（P90 = 41.3）。用 P90 判、平均值只作地板（< 6 才算整幅与底色同色）。

### 2.3 阈值来自样例实测，不是拍脑袋
`scripts/raster-check.mjs` 在浏览器里驱动**真实模块**，对一批可接受/不可接受样例打印实测表并断言。
2026-09-28 在 60px 白底下的实测（节选）：

| 样例 | 主体短边 | 平均对比度 | P90 | 判定 |
| --- | --- | --- | --- | --- |
| clear（合格：实心大叶 + 枝条） | 28.0px | 145.6 | 176.0 | 通过 |
| bud（真实库素材，薄弱） | 19.5px | 60.5 | 97.4 | 通过 |
| **star（真实库素材，薄弱）** | 25.0px | 12.5 | 41.3 | 通过（平均值低是光环所致） |
| clover（真实库素材） | 32.0px | 54.5 | 128.0 | 通过 |
| faint（退化：颜色接近白色） | 28.0px | 8.0 | 13.3 | **拦下**（P90 < 24） |
| dot（退化：缩到 60px 只剩几个点） | 6.0px | 101.6 | 148.5 | **拦下**（主体 < 12px） |

阈值：P90 ≥ 24、平均 ≥ 6、主体短边 ≥ 12px。

### 2.4 既有库存不被批量重画
本层最初只作用于**新绘制**的素材（`acceptSvg` 只被绘图路径调用）；库素材走显式引用/复用时
不经过本层复检，因此 bud / star / 四叶草这些"薄弱但可用"的既有素材不会被静默重画或覆盖。
它们只出现在校准记录里，作为阈值位置的参照。

**该口径已被 2026-09-29 质量恢复计划 §6 第二条取代**（口径变更，不是笔误）：
"复用素材与新生成素材执行**一致**的适用门禁"。原因是本口径留下一个真实缺口——
库素材读得出来就直接 `finishOk`，随后被排版层按同一套结构规则拒收，于是
"正文里没图、未完成清单却说全部完成"。现在复用路径同样过 `acceptSvg`（Tier 1 + 真实尺寸栅格），
结果按 `assetId|版本|角色|REUSE_GATE_VERSION` 缓存，**不会每轮重复昂贵操作**。

不变的部分（仍然成立）：**不达标不静默重画**——库里命中的素材没过门禁就如实记为未完成
（带固定证据与用户可见原因，可单项重试或换一张），沿用"库里命中的素材读不出来也不重画"的既有口径。
代价是对既有素材库的**可见行为变化**：某件素材在真实尺寸下不达标时，以前会静默进正文，
现在会从正文里消失并给出原因。

### 2.5 角饰提示词收紧
按上面的实测结论改了 `svg_kind_prompt("deco")`：只画一个主体、轮廓要粗（主要色块宽度
≥ 40 画布单位，约合 60px 下 8px）、透明边距约占画布 1/4、颜色明度不高于 85%。
用"扩大整幅图片"来掩盖问题被明确禁止——那会把角饰变成铺满画布的大图。

### 4.3 真机逼出来的两个问题（都已修）

**问题一（真 bug）：绘图请求的输出上限太小，导致画图**必然**失败。**

第一次跑第 ② 题时，新画横幅连续两次返回空正文。日志给出的数字是决定性的：

```
finishReason: "length"    usage.completion: 8000   responseLength: 0   耗时 35.3s / 35.6s
```

上限是 8000，而它正好用掉 8000 —— **推理开销自己就把预算吃光了，一个字都没轮到输出**。
对照同一轮的文字创作：`completion: 6525` 而正文只有 584 字，可见这个模型的推理 token
远大于产出 token。修好上限后再画一次：`completion: 18574`、产出 6874 字 SVG ——
也就是说**需要约 1.86 万 token，8000 的上限注定失败**。

这与源码里那条历史注记（"早先实测 flash 画 SVG 会推理吃光预算、content 为空"）是同一个失效模式，
只是这次的结论不靠猜：有 `finish_reason` 与 `usage` 作证。
修法是**提高上限**（`DEFAULT_NONSTREAM_MAX_TOKENS` 8000 → 32000，可用
`DEEPSEEK_NONSTREAM_MAX_TOKENS` 覆盖），而不是换模型——上限只是允许空间，模型写完就停。

**问题二（我自己的埋点有缺口）：空正文把最有诊断价值的两个字段丢掉了。**

原先 `raw_completion` 在正文为空时直接 `Err("模型未返回内容（或返回内容为空）")`，
于是 `finish_reason` 与 `usage` 在被抛出的那一刻就没了——日志里只剩"空返回"三个字，
分不出是"服务端真的给了空"还是"被截断了"。第一次跑失败时我就撞在这个缺口上。
改成：空正文**不当异常抛出**，先把 `finish_reason` / `usage` 带回去，由调用方判定失败分类。
改完立刻拿到了上面的 `length` + `8000/8000`。

顺带修了 `fake_server_cancel_stops_waiting` 里一条过于严苛的时间断言（原来卡 3 秒，
机器满载时偶发假红）：断言的本意是"没有等满服务端的 5 秒"，放宽到 4 秒仍然守得住这个语义，
但不再受调度抖动影响。

### 4.4 顺带被真机证实的两件事

- **绘图真的慢**：一次成功的横幅绘制用了 **74.5 秒**。这解释了为什么"不重复画"比"画得更快"更值钱——
  批次三让第 ③ 题复用已画好的图、绘图 0 次，直接省掉了一次 74 秒。
  也说明 240 秒的单素材位预算定得合理（74.5s < 240s，且留了重试余量）。
- **失败结果确实没被当成正文**：第 ② 题失败那一轮，界面警告是
  "已从正文中移除 1 处未解析的素材协议行（成品不残留占位/引用代码）"，正文里没有出现
  "此美术素材生成失败"这类字样——批次一的修复在真实链路上生效了。

### 4.5 上限改成"问服务端要"，而不是猜

4.3 里我把上限从 8000 提到 32000 —— 那仍然是**猜**。按用户要求"真实去查这个模型的上限"，直接问了服务端。

**查到的真实上限**（`GET /models`，2026-09-29）：

| 模型 | 上下文窗口 | 最大输出 | 输入模态 | 推理档位 |
| --- | --- | --- | --- | --- |
| `deepseek-flash`（DeepSeek-V4.1-Flash） | 1,048,576 | **393,216** | text + image | low / high / max，**默认 high** |
| `deepseek-v4-pro`（DeepSeek-V4-Pro） | 1,048,576 | **393,216** | text | low / high / max |

**猜错的两种代价都实测过**：

- 猜低 → 静默截断。上限 8000 时 `finish_reason=length` + `completion` 用满 8000 + 正文为空，画图必然失败（4.3）。
- 猜高 → 服务端 400。实测 `max_tokens=400000` → `Invalid max_tokens value, the valid range of max_tokens is [1, 393216]`；而 400 归入 `auth` 类、**不重试**，整次绘图直接失败。

所以改成**运行时查询并缓存**：`model_limits()` 打一次 `GET /models`，取该模型的 `max_output_tokens`；
查不到（离线、403、返回体异常、值为 0）就安静退回**已验证可用**的 32000，绝不让创作因此失败。
缓存键是「端点 + 模型」——只按模型名缓存会让不同服务的值互相串味（写测试时真踩到了：两个假服务同名模型
且端口被操作系统复用，断言随机失败）。

**流式档位保持不动**，只加了钳制。依据：真实桌面创作一次用掉 22,821 个 completion token，
而独立探针里 2,000 字长文只用 4,299 —— **推理开销随上下文复杂度放大，不随正文长度**。
64000 对已知样本有 2.8 倍余量，且流式刻意没有总超时（跑飞只能靠用户按停止），
所以保留原档位更稳妥。真正需要放开的是非流式那一档，因为那才是实际出事的地方。

**推理档位显式写死为 `high`**，不再依赖服务端默认（默认值可能变）。**顺带否掉了一个诱人的优化**：
把画图降到 `low` 看着能省 —— 单次采样甚至显示快 2.6 倍。但同一提示各跑 4 次、用产品自己的
`checkSvgQuality` 判定后：`high` **4/4 过闸**，`low` **0/4 过闸**（四次全部"有可见元素完全落在画布外"，
1/4/6/13 个不等），而且实际只快约 15%（42.3s vs 50.1s）。**单样本不可信**：同档位内耗时波动就有 2 倍
（32.6s ~ 71.9s）。这条教训写进了 `NONSTREAM_EFFORT` 的注释里。

**与超时的关系**：按实测吞吐（约 268 token/秒），180 秒超时约相当于 4.8 万 token。
换言之**真正兜住跑飞的是超时**，上限只负责"不去人为截断"。两者都保留。

**改动后的真机复验**（同一套隔离方式重跑第 ②③ 题）：新画横幅一次成功
（`finishReason: stop`、`completion 21238`、产出 8358 字 SVG、83.6 秒）；改正文一轮 **0 次绘图**、
两个素材位都 `reuse`。`cargo test` 101 项通过（新增 4 项：上限钳制、兜底、档位钉死、
以及"按服务端报的上限发请求"的端到端断言）。
