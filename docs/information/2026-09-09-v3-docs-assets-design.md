## 一、用户原始诉求还原

用户在 2026-09-09 提出大版本需求，原文拆成两个痛点：

1. **HTML 留不住、改不了本地文件**
   - 现状 HTML 全部"缓存在程序内，一旦关闭全部消失"，需要能**直接保存、重开之后打开这个 HTML**。
   - 智能体做修改时，要能**直接调用并修改本地的 HTML**（而不是只在一个随时会丢的会话里改）。
2. **素材是一次性的，且每次都在对话内"现场造代码"**
   - 现状素材单次生成、无法复用，每次生成都消耗大量素材代码生成。
   - 需要把**素材生成与推文生成分开**：由独立智能体生成素材；推文制作直接**复用每个用户个人素材库内的素材**。
   - 需要**独立的素材生成智能体入口**（如气泡、分割线等单独素材，各自配智能体和数据库）。
   - 需要**完整的素材搜索调用的数据库**。

## 二、已确认口径（2026-09-09 AskUserQuestion 拍板）

## 三、总体目标

V3 把产品从「一次性聊天窗口」升级为「用户个人的推文资产工作台」，两条支柱：

- **支柱 A —— 推文文档化（默认自动保存）**：每篇成品推文自动落盘为一个「文档」：真源（可编辑正文源码）+ `.html` 产物快照，用户不主动删除就一直在。可重开、可继续对话修改；AI 通过工具读写文档真源，改完自动重渲染 `.html` 并刷新文档库里的同一份文档。
- **支柱 B —— 素材资产化**：把「画图」从单篇对话的临时行为，变成「素材库 + 素材智能体」的持续资产：素材工坊独立制作入库 → 推文主智能体检索复用 → 缺素材才委托现场制作并存库 → 库自生长、越用越省。

两条支柱合起来回答用户诉求：**文档能留、能改（A）；素材分开造、反复用（B）。**

## 四、术语表

- **真源（source）**：一篇推文的可编辑正文源码。即会话里 ```v2 围栏内的文本（说明文字 + 素材引用 + 照片位），是唯一被 AI 直接编辑的对象。
- **文档（document）**：一个落盘推文产物单元 = `meta.json + source.md + article.html`（html 是 source 渲染快照）。文档是用户视角的「我的推文 / HTML」，默认自动保存。
- **素材（asset）**：可复用的单个美术/装饰资源 = SVG 矢量源 + 结构化语义元数据。分类型存于个人素材库。
- **素材快照（asset snapshot）**：文档在其 meta 里固化保存的、引用某素材时所用 SVG 的副本（连同库端版本信息），使旧文档不被库的后续改动影响（决策 D5）。
- **主文档智能体**：负责推文创作/修改的主智能体（对话工作台、文档库"继续改"的驱动者）。它只检索/委托，**不画图**。
- **素材智能体**：负责"按描述画素材 SVG"的专用智能体（沿用并升级现 gen_svg 的图像子智能体，按分类可有不同 persona/规则）。主文档智能体通过工具调用它，产出进素材库。
- **素材工坊**：独立的素材制作/管理入口（顶栏工作区之一），素材智能体在此创作。
- **素材解析器**：推文成稿后把正文里的素材引用解析为实际 SVG（优先用文档已固化快照，其次取库当前源并固化），并对无命中项委托素材智能体制作的确定性环节。

## 五、架构总览与导航形态（决策 D1）

用户确认：**文档库、素材工坊用顶栏切换**；不同工作区状态下分别是**主文档智能体**或**对应分类的素材智能体**在服务。

```
公众号推文助手（顶栏切换）
├── 对话工作台   # 现主界面：会话栏 + 与主文档智能体对话 + 375px 预览；
│               # 默认自动落盘为文档（见第六节），会话内更新刷新该文档
├── 素材工坊     # 个人素材库：选分类 → 对应分类素材智能体制作入库；检索 / 管理全库
└── 文档库       # 默认自动保存的推文文档：列表 / 打开(回到其会话继续改) / 在浏览器打开 html 快照 / 删除
```

- **对话工作台** = 主文档智能体面：创作与改稿在此发生，成品默认自动成为文档。
- **素材工坊** = 素材智能体面：在工坊内选中某分类（气泡/分割线…），服务当前任务的就是该分类的素材智能体（独立生成规则、对应子库）。
- **文档库** = 文档管理面："保存的 html 从哪重新打开"的答案；点开一条文档回到可继续改的状态（由主文档智能体承接）。

## 六、支柱 A —— 推文文档化

### 6.1 真源 = 正文源码，html 是产物（口径 1）

沿用现行确定性管线：```v2 正文（Markdown + v2 排版语法 + 素材引用 + 照片位）→ compose → 375px 自包含 html。文档把「正文源码」定为真源，`.html` 只是它每次渲染出的快照，二者同目录同 id 保存。

因此「智能体修改本地 html」在 V3 的实现语义是：**AI 用工具读/写真源文本，系统对真源重跑 compose，覆盖刷新同目录的 article.html**。模型感知的是"正在编辑本地这份推文"，而不是直接去改展开后的庞大 html（口径 1 已确认源在源）。

### 6.2 文稿与对话分离、文档默认自动保存（决策 D2 / D6）

用户确认：**文稿（文档）与对话分开存放、分开浏览**；文档**默认自动保存**，除非用户主动删除；会话内每一次更新都**刷新文档库中默认保存的那一份文档**，而不是同时保留两个版本。

- 每个创作会话默认对应一份自动保存的文档（会话与文档解耦存储，见 6.4 目录）；删除文档是用户的主动操作。
- 会话内改稿 → 同一份文档被就地更新（source + article.html 一起刷新），**不做版本分支/历史堆叠**。
- 需要另一个独立成品时，用户新建会话（自然产生一份新文档），而不是在一份文档里存多版。

> 目录布局上文档与会话是两套数据（documents/<id> 与 sessions/<id>），但通过 meta 关联（会话可反查它产出的文档 id，文档可反查来源会话 id），便于文档库"继续改"时回到对应会话。

### 6.3 存储布局（在 文档/wechat-mp-workspace 下新增 documents 区）

```
文档/wechat-mp-workspace/
├── sessions/                 # 会话消息（现状，不动）
├── exports/                  # 一次性导出（现状，保留）
├── assets/                   # 个人素材库（第七节）
└── documents/<docId>/
    ├── meta.json             # { id, title, createdAt, updatedAt, sourceSessionId?,
    │                         #   theme, sourceLang:"v2", assetSnapshots:{ <assetId>:{svg,ver} } }
    ├── source.md             # 真源：说明文字 + 一个 ```v2 围栏（含素材引用/照片位）
    └── article.html          # 产物快照：真源 v2 围栏经 compose + 素材内联后的自包含 html
```

`meta.assetSnapshots` 是**固化副本**落点（决策 D5，见 6.5 与 9.4）：每个被本文引用的素材在此存下当时用到的 SVG 副本与库端版本，重开/重渲染时用快照而非库的当前源，确保旧文档视觉不随库演进漂移。

### 6.4 保存 / 重开 / 修改链路（用户可见行为，默认自动）

- **自动保存**：会话产出（或改出）一版合规终稿 → 自动落盘为该会话的默认文档（真源 + html），文档库出现/刷新该条，无需手动"保存"。
- **重开**：文档库点开 → 预览直接显示 article.html（无需重跑模型）；点「继续改」→ 进入该文档关联的会话（历史仍在则复用，否则新建会话并预置真源），让主文档智能体接着改。
- **修改**：会话里发修改指令（改某段、换某素材、重写某气泡）→ 主文档智能体读真源 → 产出新 ```v2 → 系统重渲染 html → **刷新文档库中同一份文档**（覆盖更新，不新增版本）→ 预览即时更新。重启后从文档库打开即恢复。
- **删除**：仅在用户主动删除时文档消失（删除动作需明确范围：是否连带其会话，开发期给默认并提示，见 6.6 备注）。
- **给外部用**：article.html 始终自包含（素材以快照内联 data URI），延续第 34 轮"HTML/图片手动上传"用法；另提供"在系统浏览器打开快照"。

### 6.5 AI 改本地文档 = 文档工具（写进工具契约，决策 D7）

新增一组"当前文档/素材委托"工具（模型可调，非前端状态机，符合永久禁令 6）：

- `read_document`：读当前文档真源（+ 可选 html 摘要），让模型"看到这篇"。
- `update_document`：模型给出一版新 ```v2 真源（对旧真源的改动由模型产出全文新真源），系统落盘 source.md → 用素材快照/库源重渲染 article.html → 就地刷新文档。
- `save_document_as`：另存为一份新的文档（独立成品/改版，与"就地刷新"是两条路径）。
- `request_asset(category, desc, theme?)`：**主文档智能体唯一**的现场取料工具——把"需要什么素材"的描述交给对应分类的**素材智能体**制作并自动入库（origin=article-fallback），返回新素材 id；SVG 由素材智能体书写，主智能体绝不 inline 任何 SVG（口径 2 强化）。

> 注意：为保确定性渲染，模型**不是**自由编辑任意 html，而是重写真源由引擎重渲染（同现状 v2 契约）。"只想动一句文案"这类小改，模型读真源后只改那一句重写一版即可，成本低且稳定。

### 6.6 素材引用的固化与改版影响（决策 D5）

用户确认：**引用时固化副本**，且**改动库素材时扫描引用它的老文档，让用户逐篇选择是否更新**。

- **固化**：首次渲染某引用时，把该素材当时 SVG 存进文档 `assetSnapshots`；此后该文档任何重渲染都用快照，库素材后续被改不影响它。
- **改版影响扫描**：在素材工坊里"编辑/替换"某素材时，先跑 `scan_asset_usage(assetId)`，返回引用了它的文档列表（及其快照版本）；由用户对每篇选「更新到新版」或「保持旧版」；选更新的文档重拉库源覆盖快照并重渲染 article.html。
- **删除素材**：被文档固化引用时提示"仍被 N 篇文档引用（其内为固化副本，不受影响）"，允许删除（仅影响库，新创作不再可选它）；未被引用则可直接删。
- 文档库删除的连带关系备注：删除文档仅清文档记录与其快照文件；若其关联会话仍在并被继续使用，会再产出新默认文档——开发期把这一条的默认交互（删除时是否连会话）做成明确提示，不给静默双份。

## 七、支柱 B —— 个人素材库

### 7.1 定位与范围（决策 D3）

- **个人**：素材库是**本机、本应用**的用户私有资产（跟随 workspace 目录），不是全局共享。多账号/profile 隔离**本轮不做**（用户确认：不需要）。
- **持久**：SVG 矢量源以文件落盘，索引 JSON 常驻可搜；应用重启后素材库原样可检索。
- **自生长**：推文创作缺素材时由主文档智能体委托素材智能体现场制作后**自动入库**（口径 2 / 决策 D7），因此越用越全。

### 7.2 存储布局（workspace/assets）

```
文档/wechat-mp-workspace/assets/
├── index.json                # 全库索引（轻量字段子集，供列表与快速过滤；随增删改原子更新）
└── items/<assetId>/
    ├── meta.json             # 完整元数据（7.3）
    ├── source.svg            # 矢量源（画死色值；含 viewBox）
    └── thumb.png             # 缩略图（小尺寸 PNG，供工坊网格/检索预览；可后续生成）
```

按类型过滤交给 index.json 的 category 字段即可，不必物理分目录（每类子库以 category 分区逻辑隔离）。

### 7.3 素材条目元数据（meta.json）——语义化是关键（口径 4）

```jsonc
{
  "id": "as_a1b2c3…",            // 唯一 id（新增时生成）
  "category": "bubble",          // 分类（7.4 枚举之一）
  "name": "bubble-flower-corner",// 简短唯一名（机器/模型引用用）
  "title": "右下角一朵小花的气泡角饰",
  "desc": "浅暖色气泡角饰素材：右下角画一朵五瓣小花，花心一点黄，其余大面积留白，适用于 KEY/TIP 气泡右下角，贴图后气泡显得右下有小花。",
                                 // ← 语义化自描述（入库时由素材智能体撰写，主智能体靠它检索命中）
  "tags": ["气泡", "小花", "角饰", "右下角", "暖色"],
  "usage": "deco|wide|inline|banner|heading",   // 可被引擎放在哪类装饰位
  "placement": "bubble-corner",  // 更细的安放位（可选，便于引擎/模型判断是否合适）
  "style": ["guochao"],          // ← 软参考（口径 4）：可空、可多值、仅辅助检索，不做硬约束
  "palette_note": "主色暖色系，花心金黄",  // 配色备注（文本，不强绑色板）
  "aspect": {"w": 90, "h": 90},  // 素材宽高比/预期显示尺寸（来自 viewBox 或说明）
  "version": 1,                  // 库端版本号（文档快照靠它判断是否落后）
  "createdAt": "…", "updatedAt": "…",
  "origin": "workshop" | "article-fallback",   // 来源：工坊制作 / 推文缺料现场补做
  "usedIn": 3                   // 被引用次数（展示用，可后置）
}
```

要点：

- `desc` 是**给主智能体检索用**的自然语言描述，必须具体写清"这是什么、长什么样、适合放哪"。入库时由素材智能体起草 + 用户可改。
- `category/name/tags/desc/usage` 是检索主键；`style` 只是软标签（口径 4：风格只是参考，检索到最贴合语义即可用，不强求匹配声明风格）。
- 新增 `version`：配合文档 `assetSnapshots` 里的版本做"改版影响扫描"比较。
- V3 **不**做语义色 token 自动换色（列为远期，见 7.6）。

### 7.4 分类表（对齐 v2 引擎装饰位 + 用户举例；决策 D4）

素材分类沿 compose 引擎现有的美术/装饰位枚举（保证库有料即插即用），并覆盖用户"气泡、分割线"举例。首版实施 bubble/divider/deco/banner/heading/art-inline/art-wide/photo-frame 八类，bg/icon 后置（用户确认：同意）。引用语法见 9.3（示例代码统一列在表后，避免表格内管道符转义问题）。

| category    | 中文       | 对应 v2 安放位        | 说明                        |
| ----------- | --------- | ----------------- | ------------------------- |
| bubble      | 气泡（角饰/陪衬） | 气泡引用名（右下角角饰等） | 让气泡带装饰（如右下角小花），用户主要举例     |
| divider     | 分割线 / 花饰 | 段间分隔             | 换场花饰、分割线装饰素材               |
| deco        | 通用角饰     | deco 定义 + 组件引用    | 现 `::: art deco` 的来源       |
| banner      | 开篇横幅     | 文章头部             | 开篇主视觉插画                    |
| heading     | 小节装饰     | 小标题旁/下           | 小节路标装饰                     |
| art-inline  | 正文内嵌插画   | inline 图位占位       | 文中信息性小插画                   |
| art-wide    | 宽幅插图     | wide 图位占位        | 通栏插图                       |
| photo-frame | 照片位装饰框   | 与 photo 照片位并存     | 照片位留白时的装饰画框（第 31 轮并存口径的补充） |
| bg          | 背景纹理     | 正文底              | 背景类素材（弱水印/纹理），后置          |
| icon        | 图标/徽标    | 列表/角标            | 后置                          |

引用/占位写法示例（见 9.3）：气泡角饰 `[[asset:bubble|bubble-flower-corner|给 KEY 气泡右下角的小花]]`；图位语义占位沿用 `[[img:wide|…]]`、`[[deco:名|…]]`。分类只约束"能不能放这儿"，不做风格硬过滤。

### 7.5 检索：主智能体直接找（口径 4 / 口径 2）

- **语义检索**：新增工具 `search_assets(query, category?, style?)`。query 是自然语言（如"右下角有小花的气泡角饰"）。实现先走"标题/desc/tags 关键词 + 类别过滤 + 简单相似度排序"的确定性底，命中不足时允许一次模型轻量 rerank（可控成本）；返回前 N 条的 `{id, category, title, desc, usage, aspect, version}` 给主智能体挑。
- **工坊内的检索**：同一底层，网格/列表视图给用户浏览；也可供用户输入筛选。
- **硬约束仅保留「安放位合不合适」**（category/usage 与引用处的组件类型要匹配，否则 compose 渲染警告）；**风格不做硬过滤**（口径 4）。

### 7.6 与"风格/色板"的关系（口径 4 落地）

- 素材 SVG 颜色是画死的（现状如此）；`style/palette_note` 只是元数据软标签，供检索偏序，**不是**硬约束。
- 推文仍可有 `[[theme:…]]` 声明用于底色/文字/组件主色的皮肤渲染（现状），但素材不强制配套——一个暖色小花气泡用在非"国潮"文章里也允许，只要语义与布局合适。
- **语义色 token 自动换色**（一套矢量跨风格复用）记为远期增强：SVG 以 CSS 变量/占位色存储、嵌入时按主题注入色板。本轮不做，避免重着色引擎复杂性与渐变失真风险。

## 八、支柱 C —— 素材工坊（独立素材生成智能体入口）

### 8.1 形态（口径 3 + 决策 D1）：一个工坊 + 库内分类，由顶栏进入

素材工坊 = 顶栏工作区之一，内部是"分类选择 → 该分类素材智能体 → 对应子库"结构：

```
素材工坊
├── 分类选择：气泡 | 分割线 | 角饰 | 横幅 | 小节装饰 | 正文插画 | 宽幅插图 | 照片装饰框 | （bg/icon 后置）
├── （选定分类后的）制作对话 / 列表
│   ├── 制作：以自然语言描述想要什么 → 该分类的素材智能体按分类专属规则生成 SVG → 预览
│   │        → 校验 → 生成语义 title/desc/tags 供确认 → 入库到该分类子库
│   └── 管理：浏览本分类库 / 全文搜索 / 改 title·desc·tags·name / 替换源（触发改版影响扫描 6.6）/ 删除
└── 全库搜索（跨分类）
```

- "每个分类单独配智能体和数据库"的实现：**分类专属的生成 persona 规则 + 分类专属校验 + 分类子库索引片**，全部收在同一个工坊入口里（口径 3 的"一入口多类"）。顶栏选中工坊后，再选分类，即由该分类的素材智能体服务（决策 D1）。
- 子库物理上不强制分目录，逻辑上以 `category` 分区（index 过滤），便于将来升级成各自独立目录。

### 8.2 素材智能体分类专属规则（草案，开发期沉淀成 persona/协议片段）

沿用第 29 轮图像子智能体的"复杂度契约"（分层/结构/明暗/材质/细节、元素数门槛、viewBox、零文字零 emoji），并按分类加差异：

- bubble：关注角饰位置（如右下）、留白与气泡底色的协调、不喧宾夺主。
- divider：关注横向适配 375px、元素数适中、重复节拍均匀。
- banner/art-*：延续现有复杂度契约 + 具体可辨认（素材铁律 v4）。
- 所有素材：**SVG 尺寸与其在文章中的真实占位一致**（用现有 375 版式上下文），入库即"所见即所得"。

### 8.3 入库即带语义描述（口径 4）

素材智能体产出 SVG 后，由它（或一次轻量调用）生成：

1. `title`（简短名）
2. `desc`（具体语义化描述：是什么 + 长什么样 + 适合放哪，如"右下角一朵小花的气泡角饰"）
3. `tags`、`usage`、`style?`（软参考）
4. 预览缩略图（可选，工坊网格用）

用户可在入库前修改命名/描述。入库写入 `assets/items/<id>/` + 更新 `index.json`。

## 九、推文制作流水线改造（两个智能体组合）

### 9.1 现状（第 24/29/30 轮）

```
主模型(对话内) 写 [[img:…]]/[[deco:…]] 占位
   → 图像子智能体 gen_svg 逐个现场画（新 DeepSeek 调用）
   → 校验 → ::: art 块 → compose + artRender(PNG data URI) → html
   —— 每次创作都画一遍，SVG 不留存、不复用
```

### 9.2 目标流水线

```
[素材工坊 / 推文现场] 素材入库（素材智能体画 + 语义元数据） ──► 个人素材库(assets/)
                                                                        │
[主文档智能体创作] 需要某装饰位 → 调 search_assets(语义) ──► 命中库素材 → 写 [[asset:类型|id|用途]] 引用
                                     │ 未命中且必要
                                     ▼
                      调 request_asset(分类, 语义描述) → 该分类素材智能体制作 → 自动入库
                      （origin=article-fallback，UI 给提示；SVG 全由素材智能体写，主智能体不画）
                                                                        │
[素材解析器] 逐引用解析：文档已有该素材快照 → 用快照；否则取库当前源并固化为快照
   → 校验 → 替换为 ::: art 内联（走现有 artRender/compose 路径）→ article.html 自包含 → 就地刷新默认文档
```

关键点：

- **主智能体不画图**（口径 2 / 决策 D7）：它只做三件事——检索命中已有的（search_assets + 写引用）；需要现场制作时**调用** request_asset 交给素材智能体（严格约束，绝不自己 inline SVG）；其余交给确定性解析器。
- **缺料委托 = 自动 + 提示**（决策 D7）：现场制作不需要用户确认，完成后在界面提示"已现场制作素材 X 并入个人库"。有界：同一回合先整体检索、缺的批量委托一次，避免 5-8 个占位串行多次调用（沿用第 29 轮"回问有界/不串行全量"的教训）。
- **解析器是确定性环节**：类似现 materializePlaceholders，但"能解析就解析、缺库才委托"，杜绝每篇每次都现场画（用户的成本痛点）。
- **引用即固化**（决策 D5）：渲染时把所用 SVG 记进文档 assetSnapshots；此后重渲染用快照，不再追踪库的漂移。改库素材如需扩散到旧文档，走 6.6 的影响扫描由用户选择，而非静默跟随。

### 9.3 v2 素材引用语法草案（开发期定稿，兼容现有 [[img]]/[[deco]]）

- `[[asset:bubble|bubble-flower-corner|给 KEY 气泡右下角的小花]]` —— 主文档智能体检索后写**确定的库素材**（类型|id|用途说明）。
- `[[img:wide|…]]` / `[[deco:名|…]]` 保留为"想要的素材语义占位"，素材解析器先搜库、命中自动升级为 asset 引用并固化，未命中再走 request_asset 委托（口径 2 的兜底入口）。
- 解析器在**一个回合内**对全部素材位统一处理（先整体检索一次、缺的批量委托一次），避免串行多次调用。

### 9.4 与既有质量门禁/自检的衔接

- 现有 compose 素材用量/角饰/照片位并存等警告与 revise 自动重写回路**保留**：若真源含 `[[asset:…]]` 但库中缺该 id（素材被删/改名）→ compose 出"素材缺失"类可修复警告，自动自检让模型换一个库素材或改语义占位。
- 素材缺失的修复动作里，主文档智能体仍只能检索或 request_asset，不内联 SVG（与 9.2 一致）。
- 质检只发生在"产物层"（真源/渲染 html），不加任何对话状态机（永久禁令 6）。

### 9.5 知识库 / 引擎协议关系

- 知识库（三层）与引擎协议（engine-write-protocol）继续是"怎么写好"的权威注入，不因 V3 改变定位。
- 素材库是"画出来的成品"，知识库是"怎么画才好"的规则——两者并存：素材智能体按分类规则 + 相关知识点制作，产出进素材库。
- 可选：素材库条目可反链到其遵循的知识点条目（如 bubble 角饰参考了 module-bubble），便于将来审计，首版可不做。

## 十一、验收方向（每期拆轮后逐条细化）

- 文档化：会话产出/改稿 → 文档库自动出现同一份文档（不产生第二份）→ 重启应用 → 打开即恢复预览；会话内"改这篇某段"→ 本地 article.html 就地更新且可再次导出。
- 素材工坊：制作一个"右下角小花气泡角饰"入库 → 工坊列表/检索可见 → 改名/替换/删除生效；替换时能扫到引用它的旧文档并逐篇选择是否更新。
- 复用：新写一篇要气泡的文章，主文档智能体经 search_assets 命中刚才那个气泡 → 产物内联它且**无**现场绘制调用（可打点统计）；该文档 assetSnapshots 出现固化条目。
- 兜底：写一篇库里没有的插画 → 主文档智能体 request_asset 委托该分类素材智能体一次制作入库（带提示、不阻塞）→ 后续文章可直接复用它。
- 回归：E2E 既有 S1-S11 + 新增 S12+（文档自动保存/重开/就地刷新/删除、工坊制作入库、检索复用、缺料委托、素材改版影响扫描）；cargo 新增单测全绿；release 重建 + 冒烟。

## 十二、分期落地建议（候选轮次，开发时逐轮在 REQUIREMENTS 登记）

顺序按"先给用户最快可感知的价值、再收敛耦合"：

- **V3-R1 文档化地基**（对应痛点 1，改动相对独立、见效最快）：documents 区 + 默认自动保存/就地刷新 + 文档库入口 + 「打开/继续改/删除」闭环 + 当前文档工具（含 assetSnapshots 固化字段先行，素材引用暂仍走现状则空集）。
- **V3-R2 素材库地基 + 素材工坊**：assets 存储与 index、分类、version；素材工坊入口；素材智能体按分类制作入库 + 语义元数据；工坊管理/检索 + `scan_asset_usage` 改版影响扫描。
- **V3-R3 推文复用改造**：search_assets / request_asset 工具进主文档智能体创作；`[[asset:…]]` 引用语法与素材解析器（含固化写入）；缺料委托自动 + 提示；compose/自检对素材引用、缺失、快照版本不一致的断言；成本打点（复用 vs 现场次数）。
- 各轮均含：REQUIREMENTS 先登记 → 开发 → 单测/compose-check/E2E 新场景 → release 重建 + 冒烟 → 文档同步。
