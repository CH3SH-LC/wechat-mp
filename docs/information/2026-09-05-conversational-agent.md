# 通用对话模式——去掉固定澄清卡（第 12 轮需求报告）

日期：2026-09-05 ｜ 状态：已实施并验证（E2E 28 项全绿）

## 问题

用户验收第 11 轮"结构化需求澄清卡"后反馈：

> 这不是一个可用的智能体，为什么会有该死的固定框啊，为什么不是跟一个通用智能体一样正常对话

固定澄清卡（选项行 + 确认按钮的界面框）打断了自然对话流；用户期望的体验是
像 DeepSeek/ChatGPT 这类通用智能体一样，在同一个对话里用自然语言完成澄清。

## 形态确认（1 问）

问：要的「像通用智能体一样正常对话」是哪种范围？
- 选项 A：仅把澄清改成对话式（保留"写推文前确认"的产品定位）
- 选项 B：通用对话模式（推荐）——先像通用助手一样正常聊天，只有明确说"写/生成推文"才产出

用户选择：**B 通用对话模式**。

## 方案设计

### 路由（本地判定，App.send）
- `isDemoTopic / isCreateRequest`（needs.ts 关键词判定：创作动词+目标名词、
  祈使式、帮我/给我+动词）→ **创作模式**：persona + 知识检索，可产出 ```html 推文；
  需求模糊时模型在对话里用自然语言反问（最多 1 个关键问题）后停下等待
- 其余消息（问候、闲聊、公众号写作答疑）→ **通用对话模式**：
  `buildChatSystem` 对话人设，正常回复，不产出 HTML
- **expectRef 创作上下文标记**：创作模式下模型未产出 HTML（即先反问）时，
  下一条用户消息仍走创作模式——回答后模型直接产出推文；用户说"算了/不用了"
  （isCancel）则取消回对话。产出推文后自动复位。会话切换/清空/恢复时复位。

### 透明性（取代第 11 轮的注入注）
第 11 轮在用户消息里注入"（需求确认/默认：…）"的机械注取消。
对话即契约：模型反问与用户回答本身就是确认记录；当模型按默认推进时，
PERSONA_RULES 要求它在正文前用一句话说明采用的默认（≤25 字）。

### 模拟端（浏览器模式）
三类回复：对话人设→闲聊文案；创作 + 需求不足（evaluate.needsClarify）
+ 上一条助手未反问（不含？）→ 反问问题；否则成文样本。
按系统提示是否含"对话模式"标记路由。

### 删除
- ClarifyCard.tsx、.clarify-* 样式、App pendingClarify 挂卡分流与 confirm/skip
- needs.ts 卡片专用导出（选项表/标注函数）；describeSelections/assumptionNote 不再使用

## 验证（真实 E2E）

- S9a 模糊创作"帮我写一篇推文，主题是新书上市" → 模型对话反问（含？，无 HTML/预览）
  → 回答"日系风格，800字左右" → 直接成文，质量通过
- S9b "…直接写" → 不问，单回合直出推文
- S9c "你好" → 自然对话回复，不产出推文预览
- S9d 反问后回复"算了" → 取消回对话，不生成
- S1/S1.5/S1.6/S1.7/S2/S7/S8 全回归；pnpm build exit 0；cargo 17/17（Rust 零改动）

## 遗留说明

- 真实 DeepSeek 链路下"反问/成文"由模型按 persona 自主决定，文案质量取决于模型；
  模拟端保证 E2E 确定性。
- 创作意图判定为本地关键词启发式，个别表达（如"帮我写个标题"）可能判为对话——
  对话人设已允许模型在上下文表明创作意图时转入产出，两路都可收敛。
