## 2. 真正的产品与架构瓶颈

**交付最后一段尚缺外部验证。** `GOAL.md:35` 与 `:36` 要求公众号后台手动使用效果及安装交付；二者仍 NOT RUN。优先准备一个可丢弃 Windows 测试环境与一个可用后台草稿环境，沿用现有代表稿，不必先新增模型能力。手册仍写旧英文安装包名，跟下一次产品更新一并校正。

**分页完整不等于好读。** `src/lib/htmlToImage.ts:12`、`:60` 当前按每 1000 CSS px 整切；五页原件可见文字行被分页线切开；旧记录的 12px 实为 span 框在切线以下的 CSS 余高，并非字形损失量，详见 [分页深研](pagination-deep-dive.md#2-切字-12px的准确含义)。下一项明确产品改进可选“在接近页底的合法行/块边界切分，单块过高才兜底切分”，保留长图作为同源参照。先用冻结夹具证明无遗漏、无重复及字号实际可读，再对现有带图成品做一次 WebView2 零模型导出。

**写作可靠性需要看用户可采纳程度。** 当前四条事实断言证明指定事实保留，不证明所有新增运营陈述有来源。抽读 L8 可见“10月12日恢复正常”“线上查询、续借不受影响”等扩展内容；这里尚未逐条核对完整检索上下文，因此不将其直接定性为幻觉。后续让编辑在代表稿上标记“可直接采用 / 需改 / 缺依据”，把改善目标定为首次可采用率、改稿次数与等待时间，而非再增加若干 PASS 计数。

最小落地路径：先把这份现存稿与当次用户题面、知识工具返回放在一起，人工标注日期、政策、服务可用性、价格和联系方式的来源。只有确认缺来源后才改既有 persona/写作指令：事实只能来自用户资料与本轮检索结果；缺信息就删去细节或请用户确认，不能凭常识补具体承诺。加 3–5 份固定“仅给少量事实”的样本，先检查真正发给模型的约束，再少量真实样本；不建设通用事实引擎、不加模型调用链。人工确认可以先作为交付检查清单，不必先开发复杂的新界面。前端意图状态机禁令约束的是对话路由，不妨碍对最终稿进行已有质量检查或给用户待核对事实提示；二者不得混同。

**开发耦合集中在回合编排，不在缺少一个新框架。** `App.tsx` 约 113 KB，串联准备 (`:874`)、候选评估与冻结正文基线 (`:1297`)、修复循环 (`:1320`)、提交 (`:464`)；`chat.rs` 约 149 KB；验收驱动约 152 KB。大小只是维护成本线索，不是重写证据。真实成本来自一次修改同时碰到模型契约、候选质量、素材身份、保存与界面状态，测试层与生命周期状态难以独立复用。

## 4. 分层测试矩阵：只重复变化可能影响的行为

每次先登记“改了什么、可能破坏什么、用哪个证据回答”，再选验证。已有要求的强制检查照做；此矩阵是选择额外检查的依据，不是豁免。

| 层 | 触发条件 | 最小证据 | 不足以证明 |
| --- | --- | --- | --- |
| 静态/纯函数 | 每个有关代码切片 | 类型检查与受影响纯函数 runner；关键回归用实际失败样例 | 桌面渲染、模型表现 |
| 协议/故障 | IPC、预算、持久化、取消相关修改 | 对应真实协议/真实文件写者 + 确定性错误注入；新进程只用于跨进程语义 | 真实模型写作质量 |
| 浏览器组件 | 排版、预览、素材绑定、准备消息构造 | 冻结夹具与实际调用参数；截图、DOM、导出像素按需求选 | WebView2 特异行为、Rust 落盘 |
| release + 隔离桌面 | 每次完成代码更新，依铁律 7 | exe/setup 重建、哈希；隔离启动与正常关闭；改了导出就读回/导出既有夹具 | 安装升级与公众号后台 |
| 真实模型 | persona/知识/工具契约/模型版本变化，或出现真实模型新故障 | 受影响代表回合，派发与绘图分账；保留失败；先确认确定性驱动正确 | “永久稳定”、所有题材 |
| 外部交付 | 候选发布与用户实际使用 | 隔离安装→首次启动→设置→打开固定作品→导出；后台只存草稿/本人预览 | 自动发布授权、所有机器/账号 |

例如仅修分页：冻结长文 + 边界夹具 + 浏览器像素核对 → 按铁律重建 → 默认版对既有文稿零模型导出与正常退出。无需重新购买 L1–L4/L7/L8；既有模型证据仍标明原 exe，不冒充新 exe 已跑完整实测。若改 persona/工具声明，则跑相关真实回合；若修改跨回合保存/素材权威或多个核心边界，再触发更广的 L1–L8 集成回归。

手册资源变更会要求新 build，但不在逻辑上自动要求重跑所有付费样本。应精确写成“旧 build 的完整模型验收 + 新 build 的输入差异与安装/手册/零模型冒烟证据”，不能写“新 build 全量模型验收已完成”。

## 5. 减少等待和返工的执行方式

1. **WIP 上限 2**：一条产品交付切片、一条验证/交付设施改进。只有一名集成人拥有 App 编排与共享协议修改权；其他任务以纯模块、夹具或文档交付，避免并行改同一大文件。
2. **一次切片一次冻结**：需求与验收预登记 → 小改动 → 相关确定性验证 → 冻结输入 → release build → 零模型冒烟 → 记录哈希 → 交付。冻结后发现需要改产品，另起下一批，不能一边付费验收一边改源码。
3. **先验证驱动题面**：场景计划显式携带标题、字数区间、是否允许绘图、起始 revision、预期变化。L8 曾复用 L2 的 180 字上限而产生假红，再复用已改标题的 root 再次假红；新增场景必须先以固定输入检查这些差异，成功提交后不能假定原 root 仍是初始状态。
4. **构建只由集成人串行执行**：保留现有增量缓存，不并行争用 target，也不反复 clean。一个逻辑更新内先做完相互依赖的小修再进入 release gate，避免把每个中间编辑当成一个正式完成的更新。
5. **证据索引机器可读**：后续增加每次交付的 manifest：source/依赖/配置/fixture/test hash、exe/setup hash、runId、原件路径、检查层级、失败与未验项。稳定证据复用只限相关输入一致；路径存在与旧 PASS 不能替代身份匹配。优先解决本次大量手工翻 README/临时目录的成本。
6. **不以测试数量作产出**：每个新增检查说明其独特失败条件。已有行为用目标 runner；只有有回归风险的语义修复才补一个能变红的关键对照，不开启无穷变异/故障组合运动。

## 6. 下一批建议顺序与完成标准

**第一批：把现有包交给可试用的人。** 校正安装/手册名称；使用可丢弃 Windows 环境测一次安装与首次配置，拿已有代表稿测导出；获得后台草稿环境时验证宽度、字体、图片与分页，记录编辑是否能直接采用。无环境时保留明确 NOT RUN，产品开发可继续。

**第二批：分页阅读体验。** 交付合法行/块边界优先的分页；至少一份纯文长稿与一份既有带图稿，验证可读、无遗漏、无重复。不要先新增模型依赖。

**第三批：缩短一次成功创作的等待。** 从现有 trace 拆出准备、知识检索、正文、绘图、修复、提交的耗时与派发数，先报当前样本范围与中位数，不把总耗时笼统归因给模型。再围绕最大等待项做一项改进，目标同时看首次可采用率与重试次数；不以放宽预算换取表面成功。

**第四批：被需求带动的小重构。** 优先将候选评估或导出边界从 App 独立，保持调用顺序与持久化契约；一次只提取一个边界。chat.rs 仅在下次传输/工具契约改动时切分协议、HTTP/SSE 与业务组装，不先做全文件搬家。

本轮没有提出新增模型、自动发布、前端对话状态机或多实例并发产品能力。这些会扩大权威与验收面，应有明确用户需求再立项。

## 7. 规则变更建议，尚未生效

`CLAUDE.md:31` 的铁律 7 仍有效：代码更新验证通过后重建 exe/setup 并启动冒烟。P0 记录曾载明“本轮 scripts-only 不重建经过用户确认”；本轮只读到了该执行记录，没有读取原始授权消息，不能由此自行判断授权是单轮还是长期。后续执行者应沿用已确认的原始授权范围，无需再次询问已有授权；也不能仅凭“本轮经确认”就扩成永久豁免。
