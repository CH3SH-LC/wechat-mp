# 推文助手从本地成品到实际交付的验证方案

日期：2026-10-03。基线：`839183b`。本报告补充上一轮发展计划，回答一个尚未被本地测试回答的问题：用户拿到输出之后，还要花多少时间才能在自己的公众号使用它。下述代码事实已读取；公众号后台、真实用户与安装实验均未执行。本次未修改产品、手册或计费设置。

## 当前导出能力与用户需要之间的差距

本地导出已经有证据，继续把“能写出 PNG”作为主要产品指标，信息量很小。下一次试用应检查用户能否完成最后的编辑、核对与搬运，并愿意用同一路径做第二篇。

| 当前源码事实 | 能说明什么 | 尚不能说明什么 |
| --- | --- | --- |
| `PreviewPane.tsx:240–245` 的复制按钮调用 `navigator.clipboard.writeText(html)` | 剪贴板收到 HTML 源码文本 | 不是已实现的富文本剪贴板，不能把“复制 HTML”当成“粘贴到公众号即保留排版” |
| `exportHtml.ts:19–40` 保存 HTML 字符串；`htmlToImage.ts:29–72` 把页面光栅化 | HTML 文件与 PNG 图片是两种不同交付物 | 图片的外观保留不意味着其中的文字、电话或链接仍有原本的编辑/交互语义 |
| `exportImages.ts:32–67` 每次产出一张长图及各分页图；后端 `export.rs:166–181` 回报实际文件数并打开目录 | 用户有可找到的本地文件，文件重名也有说明 | 尚未证明用户会选对长图或分页、不重复上传同一内容，以及后台处理后仍清晰 |
| `delivery-quality.ts:1717–1718` 的 `publishReady` 是本地门禁通过且无待补照片 | 本地有限检查得出可提交判断 | 没有核对公众号草稿、手机显示，也没有证明全文所有运营承诺都有来源 |

把全文变成 PNG 会丢失原始可编辑文本与链接结构，这是光栅化路径本身的属性；微信客户端是否另有 OCR、号码识别或辅助能力，本轮没有实测，不能将平台补救能力当成产品保证。W3C 对文字图片的说明也指出，用户通常无法像普通文本那样调整字形、间距和颜色；这支持在试用中检验文字路径的必要性，而不是要求本项目立刻做一轮通用无障碍改造。[W3C Images of Text](https://www.w3.org/WAI/WCAG22/Understanding/images-of-text)

建议保持图片导出，同时验证“用户究竟需要排版图片，还是可继续编辑的图文正文”。在取得这条需求证据之前，不应直接建设新的富文本编辑器或自动发布模块。

还有一条必须分开的照片流程：`compose.ts:897–901`把照片占位和“后台替换”说明写入HTML，`photo.pending`允许保存但令`publishReady=false`；当前App以`verdict.ok`接收，导出按钮没有据此显著标为照片待补。整篇PNG会把占位也固化为像素，它没有原HTML的可编辑照片槽。成品内部有占位文字，不能说完全无提示；也未实测微信其他人工修图补救方式。[完整调用链](grounding-deep-dive.md#短附录照片占位可以保存和导出但png没有可替换照片槽)

下一交付包应明确区分“已保存”“可导出供核对”“照片已补齐”，保留草稿取回能力，不将照片待补混成质量失败候选。先用已有`pendingPhotos/publishReady`做准确状态与输出说明；真实补图路径未经验证前，不把带照片占位的PNG称为发布成品，也不靠改一句占位文案宣布问题已解决。

## 手册中必须一起校正的具体承诺

这些是下一次交付包的文字修订候选，不是本轮已经改好的产品，也不应升级为阻塞 F1/F2 的新审计项目。

1. `使用手册.html:246` 说全过程约 2–3 分钟，`:260` 说图片方式任何公众号都能用。现有记录没有相应后台及用户计时验证。建议删去未经测量的时间与普遍保证，改为清楚的操作步骤及适用边界。
2. `:197` 把绿色质量通过解释为可以放心导出。导出确实可以操作，但应说明自动检查覆盖的是哪些方面，仍需用户核对材料事实与最终读者看到的内容，不增加假装已完成的“事实认证”标记。
3. `:258` 的“把 HTML 内容复制到公众号编辑器”未说明是源码还是浏览器选中的渲染内容。当前复制按钮明确是源码文本。手册应区分两个动作；实际富文本粘贴结果留待后台试验，不能靠改文案宣布功能成立。
4. `:160` 说密钥不会上传到任何地方，`:293` 说唯一外部通信是对话到 DeepSeek。这比当前实现更强：`chat.rs:565–577` 向配置的接口地址发请求并携带 Authorization，`SettingsPanel.tsx:62–70` 允许配置接口，`lib.rs:113` 仍注册旧微信草稿命令。源码存在不等于当前界面实际调用了旧命令，但足以要求手册准确描述网络边界。建议写“密钥存于本机，请求时用于向你配置的模型服务认证；创作所需上下文会发往该服务”，并列清本地保存与联网创作的区别。

以上不需要先展开全历史隐私/安全审计。按已确认源码修订具体不准确表述即可；手册随安装包发布，按仓库既有规则完成适用构建和资源检查。

## 先做一场有判定力的交付实验

沿用已有素材与成稿，先不要为测试后台再生成一轮付费样本。安排拥有公众号草稿权限的实际使用者，使用明确的测试稿；是否发布由用户自己决定，试验只需保存草稿与手机预览。

### 第一次任务

给参与者一篇已核对事实、包含正文和一张插画的稿件及现成导出物，要求按现有手册完成选择输出、放入草稿、手机查看，并观察修改一个日期的操作成本。先独立测交付末端，不强迫为不需要AI的任务配置API。需要产品生成或续改的步骤单列，按届时仍有效的授权与预算执行；本轮不执行。研究者只观察，遇到阻塞时记录给予了什么帮助。不能由开发者代做再称“用户独立完成”。

记录一个简单结果表即可：

| 项目 | 记录内容 |
| --- | --- |
| 输入与版本 | 固定成稿及素材版本，安装包身份，后台/手机实际环境 |
| 是否独立完成 | 完成、需帮助、未完成；帮助发生在哪一步 |
| 实际时间 | 开始、完成，以及确实观察到的人工修正时间；中断时间另记，未知不推算 |
| 内容变化 | 缺字、重复、分页切口、插画、标题、联系方式、链接是否满足这篇稿的需要 |
| 真实照片 | 若稿件含照片位：占位是否仍在PNG里，作者实际在哪里补图，补完能否生成无占位成品；仅有生成插画的L7/L8不能覆盖此项 |
| 改一处的成本 | 在产品中修改后再导出，还是后台修改；需要重复哪些动作 |
| 用户选择 | 下次仍用图片、需要可编辑图文、或退回原流程；记录其原话和具体原因 |

不先建设遥测平台，也不要求使用者逐秒填表。已有请求/成品记录与一张人工观察表足够用于第一轮决策。

### 第二次任务

后续具备适用模型调用授权与预算时，让同一使用者拿自己的另一份真实材料完成一篇稿；已有授权在其适用范围内沿用，不要求无理由再次确认。禁止API调用的研究阶段只做离线编辑/交付观察，不能假装已完成第二次创作。第一篇暴露熟悉成本，第二篇才能开始观察素材与风格复用是否降低成本。两篇不构成市场统计或留存率，只用于决定下一项工程工作。

若比较旧流程和新流程，应选工作量相近的不同材料，交替先后顺序；不要让同一人第二次重复同一篇熟悉稿，再把熟悉效应全归于软件。

## 结果如何改变发展方向

| 观察到的事实 | 建议下一步 | 暂不推出的结论 |
| --- | --- | --- |
| 图片交付满足目标用户，主要卡在切字/选错文件 | 先完成安全切点、输出选择说明和一份准确手册 | 无需为了“专业”立即重写正文编辑器 |
| 用户反复需要在后台改字、复制电话或使用链接 | 做一个最小可编辑图文交付试验，保留图片路径作为选项 | 尚不能保证任意 HTML、SVG、data 图片都能被后台保留 |
| 配置 API 比创作本身更让用户放弃 | 改配置引导、连接错误说明和默认值展示，再复试 | 不能未经决策直接改 SaaS、托管密钥或更换既定模型 |
| 查事实与修规则耗时高于旧流程 | 优先 F1 材料依据合同，减少错误确定性表述 | 更多模板、插画和并发不会自动解决可信度 |
| 第二篇没有节省重新解释风格/找素材的工作 | 先优化已有风格和资产复用入口 | 不以素材库条数或主题数量证明复用价值 |

## 可交给 DS 的五字段任务卡

1. **用户结果**：用户能理解三种导出入口分别得到什么，并按准确手册完成一篇测试稿的草稿交付；资料事实仍由人复核。
2. **基线与允许改动**：当前 release 身份、`src-tauri/resources/使用手册.html`、必要导航文字；若改复制能力则另开实现包，不在手册修订中暗加功能。
3. **原始样本**：现有 L7/L8 成稿、已有长图/分页图，及本报告列出的手册与复制实现差异。先修稿中无依据承诺再用于实际用户试验。
4. **验收**：三条以内——入口描述与实际输出一致；无未经实测的时间/普遍保证；有条件时同稿完成后台草稿和手机核对，无条件则列明 NOT RUN。
5. **截止与回报**：一次聚焦修订与适用构建/资源检查后交包、手册和观察表；无后台账号就停止依赖该账号的步骤，其余独立开发继续；不调用模型生成替代证据、不群发。

本报告不改变 GOAL 的人工发布、单机创作和无前端意图状态机边界。它把“已导出”和“用户已交付”分成两个可观察结果，用后一项决定是否值得增加新功能。
