## 3. 五条具体错误链，责任分开

### A. 产品准备协议：硬限制没有成为明确、无矛盾的模型契约

R6 的3次 prep 全用于知识工具，未终结；应用正确拒绝，不是假保存。第一次修提示词要求“每次回复必须 finish_preparation”，却同时鼓励“一条回复并列取知识”，R7 L4因此把知识工具和终结工具混在一起，违反执行器互斥契约，再次失败。第二次才明确“先取资料，下一条回复再终结”。两次前端改动各触发一次 release 重建，最终 exe 再走完整 L1–L6。

归因：**产品提示协议设计/修复歧义**，不能简单归为“模型不听话”。DS 负责局部修复没有做工具组合的冲突检查；我们的指导也应在第一轮明确互斥契约及最后一轮预算，不应只要求“严格失败+再验一次”。**2026-10-03 01:16 原件勘误**：R6 是耗尽 3 次 prep 未终结的失败；最终 R8 L1、L4 各为 **2 次 prep + 1 次 gen_svg**，第二次 prep 已声明 candidate。前稿沿引进度文档的“恰好第 3 轮、提醒已发出”错误，现撤回；不能从最终样本证明只在第 3 次 prep 才追加的提醒决定了成功。逐条请求及时间口径见[关键路径深拆](ds-throughput-deep-dive.md#代表一r8-l4慢的主因不能全算给模型)。

### B. 验收脚本：拿旧场景的判据测试新场景，红了再花钱重跑

P2 长文 L8题面是300–500字，断言却沿用 L2 的≤180，合格399字被误报；修判据后在同 root 再发，标题已经由前一次成功提交改好了，“标题必须再次变化”又假红。最后用全新 root 重做 L7/L8。

归因：**驱动契约与隔离基线错误**，不是产品两次坏稿。DS 本应先用已冻结长文结果/假传输验证新参数；Codex 引入 L7/L8前也应给出“成功提交但判据失败后如何恢复输入”的规则。推荐复用已确认 L7版本的隔离副本作为 L8基线，不为得到干净测试标题再调用模型重画一次。

### C. 基础设施：先测试局部函数，真实集成路径之后才成为测试对象

事后计数被误称前置预算；挂不可写 invoke 静默失效；转挂 fetch 后漏掉 Tauri postMessage回退；修一般响应后又漏204无正文 JSON。持久化也经历“主结果假绿→附件状态不一致→失败屏障写不成→close成功但最终证据失败”。这些都有生产路径或真实协议反例，不是纯粹挑刺；但逐点修补使相同不变量多次开闭。

归因：DS 的集成验证不足；**Codex 最初拆任务也过于按文件/错误点拆，没有先冻结端到端不变量和真实协议测试夹具**。更早把“每条可计费传输前必须持久预留”“必需证据失败后下一批不得自动继续”作为两个完整事务测试，能少做几轮“模块全绿、集成再红”。最终抽出 ipc-gate 与 ledger-finalize有价值，不能把这些全部计为无效劳动。

### D. 环境诊断：从相关线索跳到唯一根因，后来回撤

CDP无端口先归因于本机 WebView2，再归因于 devtools feature；后来默认发布版也能连接，证明早先的唯一因果结论过强。profile 首轮初始化只是解释线索，部分“90秒/432毫秒”完整原件一度未定位。额外 acceptance-devtools 构建又引出“验收版不能代替默认版”的验证分叉。

归因：环境/生命周期确有不确定性，DS和审计指导都应负责**未完成同条件对照就下根因断语**。两轮无新增区分信息的等待后应停止环境试错，保留UNKNOWN，选已经能工作的默认版/稳定profile组合完成用户任务；只有新证据改变假设才追加矩阵。不得把无法复现的速度差写成保证。

### E. Codex 自己的流程负担：把每轮新发现都提升成交付前门槛

从 A–F、R1–R5、IPC/身份/屏障，到204/终结顺序，再到长稿、多页、安装、后台，任务逐次扩展。部分是守住预算、数据和真实判定所必需；长文、多页也有实际交付价值。但是**“存在未证明的边界”不应自动等于“已有可用样本没有价值，先停一切交付”**。多轮审计和文档回填占了主线，解释成本反过来继续增长。

Codex 应明确承担：旧指南顶部仍可能保留“有P0未关”，后面又追加“已关”，迫使 DS 每轮自己裁决哪个有效；各轮保留历史是对的，但当前状态不应靠长文位置推断。我们曾补充“这次是同进程新实例，非新OS进程”的证据层次修正，说明审计本身也会口头升级证据；此前 runner-negative总绿包含缺依赖BLOCKED，也必须区别真正跑到浏览器导航。我们不能只要求 DS 精准，自身也必须遵守。

## 4. 重建与再验：保留用户铁律，停止不必要的全量作废

CLAUDE.md 铁律7确实要求代码更新后重建 release+setup及冒烟；这是用户已有要求，不能擅自取消。可改进的是**把同一契约的一组修复组织为一轮更新**，先零模型证红/修复/回归，再在轮末构建，避免每改一句提示就先付费尝试。

同时，“输入哈希变化”与“所有历史业务证据失效”是两回事。P2记录因手册安装包名称旧而不改手册，理由是改 resources会使 L1–L6失效需重跑；这一理解过宽。手册更正应按要求打新包并校验安装资源/启动，历史二进制仍保留原证据，生成协议未变的部分可作为有明确依赖说明的既有证据，**无需仅因手册文字变化把真实模型全套再买一遍**。这应成为指导准则；若用户要求每个新包全套真实模型，那属于另外的显式要求。

## 5. 下一轮给 DS 的执行方式与停止规则

| 规则 | DS 必须交付什么 | 何时停止 |
| --- | --- | --- |
| 一轮一个用户结果 | 例如“拿当前包完成一篇真实待发文章并导出”，最多3个验收条件 | 达到冻结条件就交付；新发现进独立待办，不自动扩scope |
| 先分类再重跑 | 红项标为产品/模型协议/驱动/环境/证据/外部依赖之一，附一个最小原件 | 驱动假红不得新增模型请求，先用保存产物重判 |
| 先离线封契约 | 修改提示词时验证互斥工具组合、预算最后一轮、实际发送内容 | 离线未通过不进入构建/付费；不以大测试数替代关键反例 |
| 一次尝试产生一个决定 | 真实失败后输出“观测、假设、区分实验、修复影响面”四行 | 无新证据/代码变化，不重复相同付费题面；同类第二次失败转诊断 |
| 基线冻结 | 每个破坏性阶段前存 accepted revision/素材快照/题面/判据 | 成功提交但驱动失败时，从隔离基线复验，不重生上游作品 |
| 审计最多一轮主复核 | 仅按冻结不变量复核，新增阻断必须给可复现的具体用户损害 | 第二轮只复验已报缺陷；不继续搜无边界假设性边角 |
| 检查按影响面 | 提示词→prep/写稿；导出→固定夹具；文档→链接与文本；打包→包与启动 | 已通过且输入未变的检查不重复；产品未变不为脚本修复重复购买业务样本 |
| 外部依赖即边界交付 | 安装环境/后台账号没有就列NOT RUN、所缺条件与人工步骤 | 不为缺账号发明替代证明；不拖延已有包与成品交付 |
| 当前状态唯一 | 一页状态：已可用、当前阻断、已知限制、下一动作；历史只链接 | 每轮一次同步，不复制整段原因到4份文档；符合仓库必填项即可 |
| 时间盒 | 30–45分钟一次可见产物检查，预留最后10分钟交付 | 到截止时间停止新实验；交付现有产物+剩余边界，不把“再一点”无限后移 |

以上是效率建议，不直接修改永久约束。当前阶段应转向**受人工复核的小范围实际使用**：8个固定场景通过证明“有可用链路”，不能证明任意文章/任意网络/安装升级全成熟；但也不需要继续建一个更大的测试平台才能把现有成果交给用户试用。
