## 一、项目定位

### 1.1 一句话定位

一个**独立于 DSH/Cordis 运行时的本地桌面工作台**：左侧与 AI 对话——**先把创作需求逐项澄清清楚，再**生成公众号推文；右侧 **375px 手机壳实时预览**产物。成稿后除复制/导出外，**可通过微信官方接口直接发布到公众号草稿箱**（▲）。底座参考 DSH 极简智能体（persona + 知识检索 + 流式对话）与 skill 机制：知识库以"注册表 + 可调用工具"方式供模型按需取用（▲），美术素材由图像子智能体生成后插入（▲）。

### 1.2 来源与边界

- 目标：脱离 DeepSeek Harness / Cordis，做本地公众号推文创作 + **发布到草稿箱**的桌面应用；AI 直连 DeepSeek，创作知识来自 wechat-mp 三层知识库，发布走微信公众平台官方接口（▲）。
- 前置知识体系 = wechat-mp 预设 `test/knowledge` 三层结构；桌面与预设并存。

### 1.3 目标用户与典型场景（推断，待确认）

| 场景 | 用户动作 | 期望结果 |
|---|---|---|
| 从零创作 | 「帮我写一篇咖啡店开业的推文」 | 进入对话式澄清，**逐项问清**类型/风格/篇幅/结构/素材取向等 → 明确后开始生成 → 右侧实时排版预览 |
| 一次性交代清楚 | 「写一篇国潮风校园招聘推文，宣传类、800 字，按之前的模板」 | 全部要求已明确则不再追问，直接进入创作 |
| 反复调整 | 「风格不要国潮了，换杂志风」 | 未产出前随时改要求；模型据此继续澄清或重写 |
| 定稿发布 | 预览满意后点「发布到草稿箱」 | 经微信官方接口在公众号**草稿箱**生成草稿，返回可预览状态（▲） |
| 写作答疑/闲聊 | 「公众号推文怎么起标题？」 | 通用对话自然回复，不进入创作、不产出预览 |

### 1.4 核心目标 vs 非目标

**核心目标**
1. 生成"像人写的、排版合规（微信语法内联、零 emoji/渐变/阴影/外链图）"的推文。
2. 创作全程**先澄清、后生成、可视化可检验**：需求不明确不产出；产出即流式可看 + 375px 真排版 + 质量检查 + 排版警告。
3. 创作质量由知识驱动，且取用方式**由模型按需调用知识工具**（不是提示词塞满，也不靠启发式条件拼装）。
4. **发布闭环**：成稿可一键发布到公众号草稿箱（含正文图片自动上传为微信素材并替换引用）（▲）。
5. 真桌面体验：多会话上下文、本地工作区存档、应用内配置、不依赖用户机器的 DSH 环境。

**非目标**
- 发布范围限于公众号**草稿箱**与发布所必需的素材上传；不做定时群发、已发布文章管理、评论/数据等后台运营（除非后续确认）。
- 不内置浏览器渲染之外的真实发布副作用以外的能力；发布失败不应让产物丢失。
- 不用前端状态机控制澄清/路由（永久禁令，见 1.5-6）；**澄清是模型在普通对话里完成的**。
- 不做运营复盘类知识（wechat-mp 侧已归档，不入库）。

### 1.5 项目铁律（用户级硬约束，需求不可违反）

1. **独立性**：不依赖 DSH/Cordis 运行时；AI 直连 DeepSeek；知识内嵌。
2. **先记录后开发**：每轮改动先在 REQUIREMENTS.md 登记需求/验收/状态，确认后动手。
3. **密钥安全**：一切凭据（DEEPSEEK_API_KEY；▲ 公众号 AppID/AppSecret）只从环境变量/应用本地设置读取，绝不入源码或提交；`src-tauri/target`、`dist` 不提交。
4. **知识语料同步**：`src/knowledge/` 手动同步自 wechat-mp 三层库，同步记 PROGRESS。
5. **真实验证文化**：UI 用 playwright E2E 截图存证；Rust 用单测 + live 冒烟（`--ignored`）；发布链路用微信测试号/沙箱验证（▲）。
6. **绝对禁止前端对话状态机**（永久有效）：不得用任何前端状态控制澄清/路由/等待——消息一律直通模型；**澄清回合只能由模型在对话流中以自然语言自主推进**（这正是"逐项问清"的实现方式，不许做成卡片/挂卡/前端分流）。历史违例（第 11/12/13/17 轮）已全部撤销。
7. **零 emoji 内容**：产品文案与知识语料不用 emoji。
8. **文档即代码**：每次变更必须同步 PROGRESS / PROGRESS-LITE / STRUCTURE / REQUIREMENTS / docs。

## 二、系统架构

### 2.1 运行形态（同一前端，双后端）

| 形态 | 触发 | 对话通道 | 数据持久 | 应用场景 |
|---|---|---|---|---|
| **桌面（Tauri 2）** | `pnpm tauri dev` / 安装版 | Rust `chat_stream` 调 DeepSeek，SSE 增量经 `chat-delta` 回流 | 磁盘 `文档/wechat-mp-workspace/` | 正式使用（含 ▲ 发布） |
| **纯浏览器** | `pnpm dev` | 本地模拟启发式近似 | localStorage | 开发/演示双栏链路 |

### 2.2 一次对话/创作的目标数据流

**阶段 A · 澄清（▲ 多轮，不产出）**
1. 用户发消息 → 模型自主判断闲聊 vs 创作意图。
2. 判定创作意图 → **先不产出正文**，进入对话式澄清：围绕所有可能的要求维度逐项自然提问（维度见 FR-A2），一轮轮确认，直到每个相关维度都明确（用户给定或授权"由你定"）。此阶段消息直通模型、无任何前端状态（铁律 6），多轮靠会话上下文。
3. 用户随时可说「算了」取消。

**阶段 B · 创作执行（需求齐备后）**
1. 按需知识取用：模型凭注入的**知识注册表**判断该读什么，通过**知识工具**调用取用点文件（▲，见 FR-C2）。
2. 主智能体编排正文（```v2 语法），在需要图的位置写**图位占位**，不内嵌大段 SVG（▲）。
3. 素材生成：**图像子智能体**按图位清单逐一产出 SVG（具体插画，约束同铁律 v4）→ 转 PNG data URI 回填（▲，见 FR-B2）。
4. `composeMarkdown` 渲染 → 375px 预览实时刷新 → 质量终检 `checkHtml` + 排版警告。
5. 定稿可：复制 HTML / 导出文件 / ▲ 发布到公众号草稿箱（微信官方接口）。
6. 每轮结束/即时点自动存档（沿用多会话机制）。

**当前代码说明**：现状数据流仍是"请求前 `retrieve()` 一次性拼节选注入 + 主模型 v2 内联手写 SVG"（第 19-21 轮形态）；上述 ▲ 机制为待迭代目标，两者差异即后续开发内容。

### 2.4 与 DSH / wechat-mp 的关系（跨项目）

- 不共用运行时；模型配置对齐 DSH（`deepseek-v4-flash` + `reasoning_effort:max` + `max_tokens:64000`）。
- 知识同源（`src/knowledge` ← wechat-mp `test/knowledge`）。
- ▲ 知识取用与 skill 机制对齐：注入**注册表**、提供**知识工具**供模型按需取用——取代"一次性塞节选/启发式条件路由"；这是本修订对检索的核心变更（见 FR-C2）。
- 素材生成对齐"子智能体分工"：把绘图从主智能体剥离成**独立子智能体调用**，降低主智能体负担（见 FR-B2）。
- 与预设分工：预设（wechat-mp）负责真实发布链路的历史定位被本项目"▲ 直达草稿箱"扩展；预设仍可保留其生态位，桌面以草稿箱为最小发布闭环。

## 三、功能需求

### A 组 · 工作台与对话

**FR-A1 三栏可折叠工作台**（不变）
- 顶栏：品牌 +「展开/收起会话栏」+ 元信息（`知识库 N 条目`、`已自动保存 HH:mm`）+「设置」。
- 布局与会话栏规则、E2E S8 验收同现状。

**FR-A2 对话与创作一体化 + 创作前"需求全澄清"（▲ 强化）**
- 通用对话人设不变：闲聊/答疑自然回复，不产代码不产预览。
- **创作意图一经确认，必须先澄清后生成（回应修订 2、3）**：
  1. 模型判定用户在要求创作 → 本轮及后续**先不产出 HTML**，在对话流中进入澄清。
  2. 澄清维度（按创作实际需要，非死板清单逐字全问；不相关维度可跳过）：主题与切入角度；内容类型（资讯/干货/随笔/活动/促销/品牌/公告…，决定文字类还是宣传类排版与模板结构）；目标读者与发布去向（草稿箱/导出/仅预览）；**风格**（见 FR-A3，不受预置清单限制）；篇幅字数与结构偏好；配图/素材取向（数量、题材）；调性与禁忌；是否沿用某历史会话的模板/风格。
  3. **保证每个相关维度都得到明确结论**：用户明确指定，或用户对某项明确授权"由你定/随便"（视为已决，此后按该维度合理默认并**在正文前 ≤25 字一句话说明采用的默认**）。任一相关维度既未给定又未授权时，模型**继续澄清，不靠自作主张默认推进，更不得开始产出**。
  4. 澄清以普通对话自然进行（可一次问清多个要点、可小结确认），多轮记忆来自会话上下文；**禁止任何前端状态机/挂卡/卡片选项**（铁律 6）。
  5. 用户答完最后一项或说"开始写/确认" → 模型进入创作；用户说「算了/不写」→ 取消。
- 验收要点（语义级）：模糊创作请求下，模型必须先出现 ≥1 个澄清问题且**不产出预览**；多轮追问直到需求齐（补维度时继续追问而非开写）；对某维度说"你定"后按默认说明一次并可开写；E2E 需新增相应场景（▲）。

**FR-A3 模式/风格不再由界面指定，改由 LLM 判断（▲ 回应修订 4、5）**
- **移除界面的"模式三段按钮"与"风格下拉"**（auto/text/promo 三选、预置 7 风格列表都不再是 UI 控件）。
- 内容类型与**风格一律由 LLM 依据已澄清需求自主判断**：
  - 文字类/宣传类排版由已确认的内容类型派生（compose 的 `detectMode` 仍可兜底判定宣传特征）。
  - 风格按内容、目标读者、调性与发布去向匹配（知识里的"风格选型教程"作为 agent 可取的参考，不强制、不偏爱某类）。
- **风格不局限于已探索的预置风格**（回应修订 5）：预置 8 色板仍可按名引用（校园/科技/国潮/日系/极简/商务/手账/森系…），但模型可声明预置之外的任意风格（杂志/报纸/美式复古/赛博/敦煌变体…乃至自定义气质），只要渲染侧能表达。
- 渲染侧（▲ 引擎扩展点，具体方案 O-12）：正文 `[[theme:…]]` 声明风格名；预置名走色板；**非预置名要求模型附带可渲染 token**（自配色板/主色·底色·点缀与设计语言），引擎按扩展配色渲染；找不到又无 token → 给出警告而非静默回退默认。
- 验收要点：界面不再出现模式/风格控件；E2E 改为验证"模型自主选型 + 任意风格可渲染"（含非预置风格样例）。

**FR-A4 消息流展示与净化**（不变）
- 同现状：prose/code/v2 分离、源码折叠（html→「查看 HTML 源码」/v2→「查看/收起正文」）、user/assistant/error 气泡、占位「已生成推文，见右侧预览。」
- 澄清问句是普通 assistant 文本消息（无预览），同样适用净化展示。

**FR-A5 输入、busy 两档态与中断（▲ 回应修订 6）**
- 输入：textarea，Enter 发送 / Shift+Enter 换行；busy 期间按钮为「停止」。
- **busy 态区分两档**：
  - ① **思考/澄清中**：模型推理、书写文字回复（如反问、答疑）——无正文流、不刷新预览；文案如「正在思考…」。
  - ② **生成中**：模型流式产出 v2/HTML，预览随围栏闭合实时刷新——文案如「正在生成…（排版中）」并伴随质量检查。
  - 两态文案/视觉可区分，状态来自后端信号（▲：Rust 需给出"即将进入产出"的信号或在流中首段前区分），而非前端猜。
- 停止：浏览器模拟 = 真取消；桌面端现状仅停止接收、请求不可中断（**桌面真取消为待办**，O-2）。

### B 组 · 生成与排版引擎

**FR-B1 v2 排版语法 → 微信合法 HTML**（引擎现状不变；新增扩展点见 FR-A3/O-12）
- 输入 `composeMarkdown(md, {mode?, theme?})`；`detectMode` 按宣传特征兜底；输出自包含正文片段 + `plainText` + `arts` + `warnings`。
- 语法全集、拒绝项（art://、本地图、表格建议转图、>20000 字符）、验收锚点（compose-check 41 项 + E2E S1.8）同现状。

**FR-B2 美术素材：交给图像子智能体生成（▲ 回应修订 8）**
- **目标机制**：把"现场画 SVG"从主智能体剥离——主智能体在正文只编排结构与图位占位（图位 = 位置 + alt 说明 + 意向），不再手写内联 SVG。
- 图像子智能体（每次独立调用、专注"只画这张图"）：输入 = 图位说明/alt、题材意象、风格 token、知识库素材规范（module-art-assets、风格条目）与约束 → 输出一幅**具体可辨认插画 SVG**。
- 管线：子智能体产出 → 校验（带 viewBox、可见图形元素 ≥6）→ `artRender` canvas 2x 转 **PNG data URI** → 回填到 v2 正文图位占位（`@@ARTn@@` 机制沿用）。
- 调用方式：在创作编排阶段先确定图位清单（每篇 5-8 处；banner/小节/气泡角饰/换场分隔/容器邻接全覆盖；单屏 ≤1），可**并行批量**生成（也可顺序），减少总耗时；deco 气泡角饰可模板化或同管线产出。
- 约束沿铁律 v4：具体对象与结构、≥2 层明暗 + 细节纹理、禁几何剪影；意象呼应；SVG 零文字/零数字/零 emoji、透明底、低饱和同色系 ≤4 色（按风格）；PNG 尺寸/分辨率上限见 O-14。
- 收益：主智能体输出更短更稳（不再吐几百行 SVG）、token/中断风险下降、主文案质量更聚焦。
- **当前代码说明**：现状仍是主模型 v2 内联手写 SVG（第 15-21 轮）；本条目待迭代。
- 验收要点（▲）：一次创作中素材图均来自独立图像调用而非正文手写 SVG；素材数量/覆盖率/达标率断言保持；真实模型 live 产物插图具体可辨、0 警告。

### C 组 · 知识库与取用

**FR-C1 三层知识语料（src/knowledge，149 文件）**（不变）
- 结构与分布同现状（00-GUIDE 路由总表 + 文本/视觉/插图/其它 → 方向 → 00-索引 + 点文件）。

**FR-C2 知识取用：注册表注入 + 知识工具按需调用（▲ 回应修订 7，核心变更）**
- **不再"一股脑注入"**：创作前不再把可能命中的多条点文件全文拼进 system prompt。
- **也不再"启发式条件注入"**：不靠前端对请求做关键词/路由裁剪后挑选 topK 塞入。
- **参考 skill 机制**，改为两步：
  1. **注入注册表**：system prompt 常驻一份**轻量知识注册表/路由目录**——把 00-GUIDE 与各方向"00-索引"浓缩为目录：方面→方向→点文件名 + 一句用途 + "什么情况读它"。模型据此知道存在哪些知识与去哪取，但**不附带正文**。
  2. **提供知识工具**，由模型在创作中按需调用取用正文（取用结果作为该环节权威细则）：
     - `load_knowledge(name)`：读指定点文件全文（如 module-bubble、style-guochao）；
     - `search_knowledge(keyword)`：按语义/主题词检索库内相关点文件清单；
     - 快捷件（可选）：`type_template(类型)`、`style_spec(风格)`、`compliance(营销类合规红线)`、`cover/readability(...)` 等映射到 C1 对应文件。
- 调用时机由模型自主：澄清确定类型/风格后 → 取类型模板 + 风格色板；写到某组件/素材时 → 取模块规范；营销类 → 取合规红线。prompt 主体保持轻量，只有真正用到的知识进上下文。
- 呈现：会话里可显示"已取用知识"命中提示（可选保留，替代现状顶部知识命中行）。
- 传输与协议待定（O-13）：DeepSeek 工具调用循环的编排位置（Rust function-calling 中转 / 前端透传轮询）必须**不引入前端对话状态机**（铁律 6）。
- **当前代码说明**：现状为第 19-21 轮的单次 `retrieve()` 注入；本条目待迭代。
- 验收要点（▲）：system prompt 不再含大段知识正文而只含注册表；真实创作中模型确实触发知识工具且产物体现类型模板结构/风格色板/合规红线（可对比同主题注入 vs 工具两条路线的命中一致性）。

**FR-E3 应用内配置**（API 设置现状 + ▲ 公众号设置）
- API 设置（Key/端点/模型）：现状不变，桌面 `settings.json`/浏览器 localStorage，优先级 env > 设置 > 旧 `~/.dsh`（仅 key 回退）。
- ▲ 新增"公众号配置"：AppID/AppSecret 本地录入（掩码、可保存/恢复/清除）；接入 access_token 获取与缓存刷新（缓存于内存/本地，过期自动刷新）。凭据安全同铁律 3，绝不明文入库/提交；存放位置（settings.json vs OS 钥匙串）见 O-16。

**FR-E4 发布到公众号草稿箱（▲ 新增，回应修订 1）**
- 前置：已配置公众号 AppID/AppSecret；发布目标固定在**草稿箱**。
- 动作（产物定稿 →「发布到草稿箱」按钮 → 后端 publish 流程）：
  1. 取/刷新 `access_token`（appid+secret 换取；缓存复用）；
  2. **图片处理**：正文若含图（data URI/占位），先经 `material/add_material`（永久素材，image 类型）逐张上传为微信 CDN URL 并替换正文引用——微信草稿正文不接受 data URI/外链直链（O-15）；
  3. 组装草稿正文（沿用 compose 产出的内联 HTML，按草稿接口 content 规则清洗非法节点/URL 后）调用 `draft/add`；
  4. 返回结果：草稿成功（可在公众号后台草稿箱看到/继续群发）或分环节错误（token 失效/素材上传失败/接口限流…），给出可读提示；**失败不丢产物**（本地 HTML 始终保留）。
- 合规/约束：图片素材类型与大小符合微信限制；发布链路需微信测试号做真实验证（铁律 5）。
- 验收要点（▲）：E2E（mock 接口层）+ 微信测试号 live：含图文章成功入草稿箱且图可访问；无图纯 HTML 文章正常；token 失效自动刷新；发布中断时产物仍在本地可导出。

## 五、非功能需求

- **NFR-1 安全**：API Key 与 ▲ AppSecret 仅本地保存，不入源码/提交；access_token 只作运行时缓存；输出 HTML 自包含/无 script；capabilities 最小化（新增发布走 Rust 命令，前端不直接拿 token 调微信）。
- **NFR-2 性能**：知识懒加载保持；▲ 知识工具使 prompt 更轻（正文按需取用）；▲ 图像子智能体并行批量以控延迟（并发与费用权衡 O-14）；流式 24ms 级增量不变。
- **NFR-3 兼容**：产物微信后台可接受；▲ 草稿箱接口对图片必须为微信 URL（发布管线负责上传替换）；导出自包含 data URI 能力保留（两种渠道并存：桌面发布走真实素材、复制/导出仍可自包含）；Windows/Tauri、窗口 1380×880(min 1000×640)、端口 1420。
- **NFR-4 健壮性**：损坏回退、检索失败不阻断对话（▲ 工具调用失败有重试/降级说明）、素材渲染失败回退 svg、防竞态（artSeqRef/bootRef/StrictMode 互斥）——同现状并扩到 ▲ 新链路。
- **NFR-5 可验证性**：E2E/compose-check/Rust 17 单测 + live 冒烟沿用；▲ 新增断言：澄清"不全不问完不产出"、无界面风格控件、素材来自子智能体、知识工具触发、发布接口（mock + 微信测试号）。
- **NFR-6 语言与调性**：零 emoji、UI 中文、无外网资源依赖（仅 LLM API + ▲ 微信 API）。

## 六、约束与技术决策（含目标态决策项）

1. 技术栈：Tauri 2 + React 19 + TS + Vite；Rust（reqwest rustls）承载 IO；pnpm 11。
2. 模型：DeepSeek `/chat/completions`，`stream:true`、`reasoning_effort:max`、`max_tokens:64000`、`deepseek-v4-flash`。
3. 创作协议：模型产出 ```v2 正文 → compose 确定性转 HTML（不直接写 HTML）；```html 直通保留。
4. 无前端对话状态机（铁律）——澄清靠 persona 约束模型在对话里完成。
5. ▲ 知识 = 注册表注入 + 模型自主工具取用（对齐 skill 机制）；取消单次大注入与启发式条件注入。
6. ▲ 素材 = 图像子智能体（独立调用画 SVG→PNG 回填）；主智能体只编排。
7. ▲ 发布 = 微信官方接口直达草稿箱（token + 素材上传 + draft/add），最小发布闭环。
8. 预置 palette 保留；▲ 任意风格经模型自带 token 扩展渲染。

## 七、代码读后观察与待议（作者标注，非定稿需求）

> 现状代码级观察（O-1…O-10 为代码实况）与本次修订衍生的设计待定（O-11…O-16）：

- **O-1** persona 字数口径不一致：对话条款"800-2000 字" vs 输出协议"1500-2500 字"（第 21 轮加长后未同步）。需统一。
- **O-2** 桌面无"真正停止"：`stop` 仅浏览器 mock 有效；桌面 Rust 流不可取消（invoke 无法 abort）。若需真取消要加 Rust 侧 cancel（修订 6 的两档 busy 与停止也依赖它）。
- **O-3** `chat-error` 事件休眠监听（Rust 从不 emit）；错误经 invoke reject→catch。冗余或预留。
- **O-4** `rename_session` 命令已注册但前端无改名 UI；标题靠首条消息派生。改名是需求候选。
- **O-5** deco 预置 `DECO_MAP`（grass/blossom/leaf）在桌面会被当"未定义角饰"警告（引擎只认 `::: art deco` 现场注册）。或清理或自动兜底。
- **O-6** 桌面工作区路径硬编码英文 `Documents/wechat-mp-workspace`（未走系统已知文件夹 API）。
- **O-7** 桌面端空态示例/违规演示 chips 会真实发请求：演示话题是浏览器 mock 专用，桌面点会打真模型（不真违规），语义不完全对齐。
- **O-8** SSE 解析不冲刷 EOF 残留（仅处理换行结尾完整行），缺一个单测。
- **O-9** `reasoning_content` 被丢弃不显示（正确），随服务商差异需留意。
- **O-10** 流式中途复制/导出取的是当前已渲染产物——符合直觉但未成文约束。
- **O-11** 澄清"何时算问完"的判据：由模型自然语言收束（小结需求并开始/待确认）——需要 persona 措辞与 E2E 验收定义，避免无限追问或提前开写。**此点是修订 2/3 落地的关键行为契约，建议先于代码明确。**
- **O-12** 非预置风格的渲染载体：`[[theme:…]]` 语法如何承载扩展键（模型自带色板块：主色/底色/点缀/气质语言），compose 扩展点与校验（找不到名的警告策略）待设计；预置色板是否也允许被模型覆盖。
- **O-13** 知识工具协议：DeepSeek function-calling 支持度与编排位置（Rust 中转函数分发 vs 前端透传——**须不引入前端对话状态机**）；工具循环中增量事件与"检索中"提示的形态；工具调用失败降级策略。
- **O-14** 图像子智能体成本/延迟：每图一次独立模型请求（费用≈乘 N），并行上限、失败重试、超时；deco 角饰是否模板化免调用；PNG 分辨率上限（现 >2000px 回退 svg）。
- **O-15** 发布管线素材上传：永久素材接口（额度/类型/大小）、data URI→material 上传后 URL 替换、发布失败保留本地产物；微信测试号可用于真实验证；草稿 content 中表格/链接等是否需前置清洗。
- **O-16** 公众号凭据存放：AppSecret 明文本地文件 vs OS 钥匙串；与现有 settings.json 明文的取舍（建议 AppSecret 至少走钥匙串或加密，见铁律 3 扩展）。
